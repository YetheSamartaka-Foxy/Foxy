\## Core conventions (Turso)

D24 durable ownership is an explicit same-process promotion of a prepared isolated parent-bound owner. Protocol8 authenticates `lifetime` and nonsecret `launch_id`; launch identity never grants authority. Confirm exact scope/launch and Detached mode before releasing the parent pipe. Parent EOF then leaves native sessions, physical leases and the exclusive DB claim intact. Terminal foreground owners cannot be promoted. Owner shutdown admits only zero sessions, no pending runtime/deployment work and a drained operation lock; it never implicitly stops a server. Reconnect restores authenticated current snapshots and bounded per-generation event replay, not PID-derived state. Explicit consumer recovery after owner death is covered below; OS services and automatic owner restart remain unavailable. Windows prepared-owner launch clears ambient controller standard-handle inheritance so captured pipes reach EOF; Rust `Command` duplicates explicitly inherited stdio independently. Linux prepared owners have their own session.

\### Data access

Native installation channel is separate from Steam branch. Reforger stable/experimental select dedicated apps 1874900/1890870; plans bind game, channel, app, branch and platform. Existing schema-v1 managed receipts without a channel mean stable, and an app/channel mismatch is invalid. Update/Repair inherit the installed channel and refuse an explicit change before provider access; fresh Install may bind another channel only through a separately reviewed new folder. Immutable predecessors, peer bindings and committed runtimes stay unchanged. Only Steam Common Redistributables from shared app 228980 are an external host prerequisite; otherwise-applicable unresolved shared payload depots fail selection rather than silently omitting required content. Package integrity never enrolls a new executable into the native runtime acceptance matrix.

The Arma mission library stores stable source identities and immutable full-PBO revisions beneath the captured space's `server/mission-library/`. Imports/acquisition preserve sources and use the offline metadata write permit; cycle entries pin exact library revisions. `ContentStageManifest.missions` binds enabled selections to owned source wrappers with their normal source/destination basenames; records verify these refs against the archived configuration, and preparation/runtime consume only verified stage bytes. Refresh changes the library pointer, never a saved cycle pin or committed runtime. Disabled entries do not render or require artifacts; addon class identities remain explicitly unverified and cannot be inferred from a PBO filename. Bounded metadata is literal-only, and direct HTTP acquisition has independent wire-byte/hash/cancellation and dry-run contracts. See [missions](../wiki/Arma-Server-Missions.md).

Configuration imports use bounded UTF-8 cfg spans without preprocessing or execution. Operator files retain unknown bytes while secret assignment values become canonical references; managed conversion is explicit and refuses inherited/append semantics. Review/apply binds captured context, revision, source bytes and redacted fingerprint. Credential records are immutable and instance/context-scoped, using current-user DPAPI on Windows and same-user private Linux modes. Resolve only the committed runtime's verified server/basic bindings inside the retained pre-spawn callback, under `deployments/runtime-state/home/private-configuration/<runtime>/`; never put values in archives, packs or arguments. Profile secret directives block native activation. Portable `.foxyserver` imports create a new unbound identity and retain source/path hints solely as unresolved intent. See [configuration import](../wiki/Server-Configuration-Import.md).

Installation build observations are ephemeral, outside `servers.json`. Inspect Windows ProductVersion as bounded data through the OS version API, never by launching the executable. Arma Steam metadata must come from a bounded strict KeyValues manifest whose canonical install directory exactly matches the captured installation; local app/build/branch claims remain advisory. Recheck executable evidence around observation and keep missing/conflicting fields unknown. `tested_engine_layout` matches only the compiled native acceptance matrix by game, platform, executable size and BLAKE3; its tested runtime version is distinct from installed metadata. Unknown/changed binaries stay unsupported, including older builds whose fallback has not been tested. Compatibility observations grant no package, vendor, materialization, activation or lifecycle authority. Root-relative mission and additive key directories still need exact instance-owned materialization and admission; adopted-root writes are never implied.

`server/owner/` hosts a foreground metadata owner with the captured per-space DB claim and no Turso engine. GUI-owned children use a protected parent stdin lifetime; explicit `server supervise` is an integration owner exempt from the parent's app-global config lock and may read but not rewrite app-global settings/selection. The desktop retains that config lock. Discovery lives outside game/install/config data in a strict private same-user runtime namespace; its canonical root/space/game key, schema, scope, endpoint and capability are validated before OS-authenticated mutual attachment. Under both the real operation and DB claims, a replacement can retire only exact valid crashed metadata-owner evidence and its known ordinary owned0600 Linux socket. Preserve malformed, foreign or replaced entries. This metadata-owner cleanup is separate from native consumer recovery and never implies game-process cleanup.

An authenticated metadata permit is deliberately narrower than a database claim. The controller first holds the stable protected operation lock, authenticates exact owner scope and obtains MetadataPermit admission. Its retained Arc/write pins keep that lock through all copying, final writes, cancellation cleanup and worker join. Only explicit offline server-store paths, including mission-library publication, use `owner::with_write`/`pin_write`; activation and Turso continue requiring the actual local DB claim. Remote write guards reauthenticate the captured owner generation. Without an owner, CLI saves use the existing temporary exclusive claim. Inspection/plan/dry-run CLI commands acquire no permit, start no owner and remain write-free. Do not unlink or replace operation lock files. Owner exit/replacement drains this lock before releasing/reclaiming space ownership; a disconnected controller cannot be treated as finished while its retained worker still holds the file. Metadata RPC admission executes no mutation, launches no process and never grants DB access; revision/fingerprint checks still run in the shared core implementation.

Client/Server handoff first finishes mutating work and flushes captured persistence, then closes client dispatch admission, advances result generation, stops/joins the watcher and reaps every retained DB-capable worker. Include startup recovery, profile backup work, backup cleanup and all tracked query/scan/hash/metadata/workshop/benchmark/import workers. Only the actual engine close can release the client claim; outstanding seam users, handles or pins refuse transfer. Keep client admission closed throughout Server mode. Startup repair, schedules, periodic probes, retries and DB-backed common settings must not reopen Turso. A transition failure retains the old owner/space or explicit closed-admission retry state. Returning to Client requires a fresh verified claim/resume and client reload. A Server space switch prepares/authenticates its target before activation and retains the previous owner until that succeeds. Close joins owned foreground owners; attached terminal-owned owners are not stopped. Retain timed-out cleanup handles and retry with bounded backoff until their operation drain is witnessed. Parent-bound GUI-owned native lifecycle sessions require zero active sessions before mode or space transfer. Explicit detached owners survive space transfer and retain their original DB claim, so same-space Client return refuses while they exist.

Dedicated-server definitions live outside Turso in `core/server/` and each space's `server/servers.json`. Pure reads/plans perform no writes. Server CLI mutations retain captured-space authority through a local claim or authenticated metadata permit without opening Turso or changing remembered selection. Adoption observes expected native headers and a bounded executable fingerprint, grants no file-management authority and rechecks evidence before save. Engine version/channel, package integrity and actual runtime behavior remain unverified.

Native Steam session credentials are separate from server drafts, owner state, and Turso. `foxy-supervisor::control` is the single version 9 local owner protocol. It is a synchronous worker API, never UI-thread or async-executor I/O. Bind every handshake and authenticated envelope to the exact config-context fingerprint, game space, instance, owner identity and nonzero owner generation. Same-user OS identity is necessary: Windows uses a first-instance, remote-rejecting pipe with an exact-user owner/DACL and identification-level client-token SID verification after a bounded preamble; Linux uses a short Unix socket in an existing same-user0700 directory, a0600 socket and kernel `SO_PEERCRED` on both ends. No PID or discovery document is authority. Peers must additionally prove an in-memory32-byte capability through fresh mutual challenges and keyed BLAKE3 domain-separated MACs. Each connection derives a fresh key and has independent strict directional sequence counters. Capabilities have redacted Debug and no Serialize implementation. Only the strict private runtime handoff stores the connection key, under explicit same-user owner/DACL or0700/0600 permissions; no argv, normal output, log or export contains it. The control library authenticates transport; core/server/owner owns GUI/CLI attachment and metadata admission.

Length-prefix bounds precede allocation (64KiB message,1024-byte result/event payload). Reject unsupported versions, unknown fields, invalid identities, scopes, MACs, sequences, event order and response correlation. One client request is outstanding per connection. A caller-supplied absolute I/O deadline and cooperative cancellation apply to handshake, connect, accept and transfer; failed/partial channel I/O poisons the connection. Windows cancels and drains owned overlapped operations before freeing their buffers; never use a blocking pipe flush. An authenticated close receipt lets the server disconnect only after the client consumed its final response. Linux cleanup preserves existing or replaced unknown endpoints; the private namespace assumes cooperating same-user processes, not protection from a hostile process already running as that user.

Retain one `Ledger` for the entire owner generation across reconnects, with at most32 logical clients and32 unacknowledged requests per client. Exact `(client_id, request_id, canonical typed operation)` retries return pending or the retained completed result and never re-execute; a changed operation conflicts. Record completion before sending it. Pending and unacknowledged completed work is never evicted: return capacity until the client acknowledges a completion. Retired/skipped IDs at or below the client high-water mark return expired, never new acceptance. A disconnect/deadline is an unknown delivery outcome, not proof an accepted operation failed. Recover only the exact old request identity; never automatically invent a new ID to repeat an effect. The bounded128-event ring returns at most8 ordered events and explicit retention gaps; reconnect preserves the event cursor and exact owner scope. Recreating a ledger requires a new owner generation and capability. This is in-memory recovery within an owner lifetime, not durable job replay or crash recovery. Inspect and MetadataPermit return authenticated snapshots/admission and execute no file mutation or engine effect; their connection-local requests do not consume the effect ledger. ActivateDeployment, ResolveDeployment, StartInstance, StopInstance, RestartInstance, StartHeadlessClients, StopHeadlessClients, RestartHeadlessClients and their cancellation operations use the retained effect ledger and sealed owner worker. Lifecycle authority is limited to the reviewed exact native runtime and validated run generation; authentication alone grants no lifecycle authority, installation lease, database sharing or engine readiness. Metadata writes remain reviewed core operations under the retained operation permit, not generic wire commands.

Scheduled maintenance (`src/core/server/jobs/`, executed by `owner/maintenance.rs`) is owner-internal: no OS service, task or second process runs jobs, and nothing runs while no owner holds the space. The per-instance catalog `maintenance/jobs.json` (at most16 jobs) is a revision-checked metadata write under `owner::with_write`; every real change advances the job's policy revision and its `revised_unix_ms`, and scheduled times before that never run. Each occurrence is a durable record `maintenance/occurrences/occ_<32hex>.json` whose id is derived from instance, job, policy revision and trigger, claimed with create-new plus fsync so one scheduled time runs at most once across ticks and owners. Updates are bound to the claiming owner id and generation and never rewrite a terminal record. Write `running` durably before submitting the effect; on startup an owner turns every non-terminal record of another owner into `unknown`/`owner_lost` and never re-executes it. Keep at most64 terminal records plus each job's latest scheduled record (deleting it would let that time be claimed again), never prune open work, and leave unreadable records in place without stopping retention. The owner claims due times on every scan, even while an occurrence runs, records a time that meets another open occurrence of the same job as `skipped`/`overlapping_occurrence`, then evaluates every ready occurrence until one becomes active, so a long deferral never holds back other work. Grace is at least one minute because scans are seconds apart, and a claimed occurrence that cannot start within grace plus deferral is skipped as missed. Decisions (`scheduled_due`, `claim_expired`, `restart_step`, `after_attempt`) are pure functions: restart is the only executing action, it submits `RestartInstance`/`StartInstance` through the internal ledger client `maintenance` with the reviewed start plan and the operation-file lock, and it never starts a server this occurrence did not stop. After each attempt record the observed run generation; a retry whose run generation moved since then was started outside the job and is skipped, while a restart whose stop succeeded and start failed retries with start only. A changed or removed job cancels its open occurrences except one that already stopped the server; a catalog read failure leaves occurrences untouched. Update and backup occurrences stay `blocked`/`adapter_unavailable`. `RunMaintenanceJob` (revision-checked, returns an existing open occurrence; the manual trigger binds owner id and generation so a reset request cursor cannot collide) and `CancelMaintenanceOccurrence` are effect-ledger operations whose 1024-byte reply carries the occurrence id and state. Before a queued app installer replaces the binary, the desktop checks every server-capable space off the UI thread and waits while an owner has active sessions, a detached lifetime or cannot be inspected; only a missing or dead owner counts as none.

`foxy-supervisor/` owns game-independent foreground process, installation-lock and session primitives. Windows uses creation-time `PROC_THREAD_ATTRIBUTE_JOB_LIST`, suspended token verification and an unnamed non-inheritable kill-on-close job without breakaway flags. Reject elevated/unknown owners; do not reuse the client's PID-returning elevation fallback. Observe both the retained root handle and job active-process count. Exit code 259 is a valid completed exit when the process handle is signaled. Wait timeout retains ownership; explicit force is save-uncertain.

Linux uses `clone3` user/PID namespaces with an owned pidfd. A dedicated creator thread outlives the requesting worker; namespace init has a parent-death signal tied to that retained thread, reaps every descendant and makes kernel namespace teardown contain `setsid`/double-fork descendants. Map only the same numeric UID/GID, deny setgroups, drop capabilities and set no-new-privileges before execution. Reject root, mismatched saved/effective IDs and capability-bearing owners. Close unrelated descriptors before payload execution, preserve closed stdio and use only prebuilt inputs/raw async-signal-safe operations after clone. No process-group fallback. Missing/denied APIs or namespace policy fail closed. The reported host PID identifies namespace init, not the payload, and grants no authority. `TreeExit.root_exit_code` is optional: forced namespace death can leave payload status unknown. Read-only support describes API prerequisites; only actual spawn proves admission. Native fixture tests do not prove engine, Steam/BattlEye, `/proc`, distribution or service compatibility.

\- Persistence is the **Turso** engine (pure-Rust, async-native, SQLite-compatible). There is **no SeaORM/sqlx and no `entities/`** - all DB access goes through the seam in `src/core/db/` (`FoxyDb`, `DbTxn`, `OwnedDbTxn`, `DbRow`, `DbValue`, `params!`, `DbErr`). Get a handle with `context.db()`; read with `query_one`/`query_all` + `DbRow` getters, or `DbTxn::query_each` when the caller builds its own structs from the rows (`query_all` holds every `DbRow` while the caller builds a second representation of the same data; the model tree's part rows are the largest such read Foxy performs, and streaming them halves that peak); write with `execute`/`execute_retry`/`transaction`. Never reach for the raw `turso` API outside `db/` and `tasks/db_turso.rs`.

\- The database is **per game space**. `db_turso::database_file_path()` resolves `database.db` from `spaces::active_game_space_dir()`, and the process-wide handle is a slot keyed by that path so a runtime space switch opens the target space's database. Anything cached per database (the shared background context, one-time maintenance passes) must be keyed the same way - never a bare `OnceLock`. See `conventions/GAME_SPACES_CONVENTIONS.md`.

\- Game-space isolation is by directory, not by a `game_id` column. Do **not** add one to `repositories`; the `(remote_url, local_path)` identity rules stay exactly as they are.

\- **One operational process per configuration root.** Claim `tasks/config_process_lock.rs` before loading, migrating or saving shared configuration, including commands that target another game space. A second owner exits `DATABASE_BUSY`; no cross-process queue is offered. Explicit integration helpers and standalone server tools remain exempt. The database and physical-target claims below remain defense in depth for independent roots and external interference. Do not delete lock files to bypass a claim.

\- **One process per game space database.** Turso has no multi-process access. `tasks/db_process_lock.rs` holds an advisory lock on `database.lock`; only an acquired claim permits access. Busy retries for 5s then refuses (CLI code `6`); unavailable locking also refuses (CLI code `4`, a separate close-only GUI explanation). The Client GUI claims at startup and space reload; Server GUI delegates the claim to its foreground owner without opening Turso. Database-using CLI prepares the remembered space before claiming, and the DB opener is a fail-closed backstop. DB-free exemptions name implemented leaves: `agent-gui`, `steam-helper`, `server inspect-addons`, `server context`, and `version`; `ui` has its own startup claim.

\- **Close before transferring ownership.** `tasks/db_turso/lifecycle.rs` serializes explicit admission, open and close. Close takes the DB exclusive barrier, DB slot, context cache and outgoing pool in that order; nonblocking refusal keeps ownership when work is active. Invalidate the cached background context, drain only that DB's idle connections, and use `Arc::try_unwrap` to prove its engine has no remaining handle users. Checked-out pooled connections retain a handle until their resources drop. On failure restore the same slot and retain the claim. Successful close suspends lazy reopening; explicitly claim/resume the selected path before new access. `acquire` never replaces another path's claim. Worker shutdown and generation-scoped results are additional requirements for future GUI/supervisor IPC handoff; this primitive alone does not prove that handoff.

\- **The sidecar is not the schema.** `db_schema_version.rs` records the intended generation, but the bootstrap is applied with `CREATE TABLE IF NOT EXISTS`, so it no-ops on an older database and leaves the old tables. `tasks/db_schema_check.rs` probes the live database on every open: column coverage parsed from `sql/turso_schema.sql`, parse-only production upserts, and unique-index column sets for repository, pending-update, addon, and file identities. A composite UNIQUE does not make an obsolete URL-only UNIQUE safe: both must be checked. Keep upsert constants shared between the production write and the probe so they cannot drift. A successful live wipe removes legacy `file_subfiles`, validates the rebuilt schema, then records the current generation. Schema generation remains 25 for 1.2.1; a healthy 1.2.0 database needs no new wipe. A fresh install's generation is recorded by the database opener itself (`bootstrap_if_fresh` in `open_and_prepare_database`) before it creates the file, because any CLI command can be the first to open it, and a populated database without a sidecar reads as one built before versioning.

\- **Postponing repair does not clear it.** An outdated or incompatible database remains repair-required for its game space until a wipe succeeds. The startup warning can be dismissed so Foxy and game Launch/Join remain usable, but repository/mod checks and updates, including background startup scans and CLI checks/updates, stay blocked. Gate those operations before database-dependent work or download side effects. CLI game launches remain allowed. A failed wipe keeps the repair requirement; dismissing a prompt or continuing one launch without wiping must not record the current generation or clear that requirement. Launch addon matching must remain usable without reading the incompatible database. See `conventions/UI_CONVENTIONS.md` for the separate final-action reminder and continuation rules.

\- Keep DB logic under `src/core/`.

\- Prefer small query helpers with clear inputs and outputs.

\- Avoid over-generic helpers unless there are at least two real call sites.

\- `PRAGMA foreign\_keys = ON` is enabled on every connection (`db_turso::connect_tuned`). `ON DELETE CASCADE` (baked into `sql/turso_schema.sql`) fires automatically - keep this in mind when writing DELETE queries or reasoning about orphaned rows.

\- **Tuned connections are pooled per database** (`db_turso::connect\_pooled`); the seam borrows one and returns it on drop. A `Database::connect()` in Turso 0.7.2 builds a fresh pager, blocking-reads page 1, opens and closes a read transaction and deep-clones the schema, and the engine's compiled-statement cache dies with the connection - a per-call connection costs 61 µs on a small read against 5 µs on a pooled one with a cached program. `TunedConnection::prepare\_tuned` admits a SQL shape to that cache on its **second** use and caps it (the engine's own map is unbounded, so one-off `IN (?, ?, ...)` shapes must not pin a program each). Two rules keep this sound: a connection that is not in autocommit is dropped rather than pooled, and any DDL bumps `bump\_schema\_epoch()` so every pooled connection is retired - a cached program is only rechecked against its own connection's schema snapshot, which is refreshed only when a statement is compiled, so DDL that happened *around* an idle connection would otherwise leave it serving programs built against dropped roots. A caller that changes connection-scoped state (the purge's `foreign\_keys = OFF`) must call `retire()`. Use the unpooled `connect\_tuned` for bootstrap and compaction. `FOXY\_DB\_POOL\_IDLE` caps the idle set (default 8; `0` disables pooling for an A/B).

\- Only the PRAGMAs Turso honors are set, per-connection, in `db_turso::connect\_tuned` (`foreign\_keys`, `synchronous`, `temp\_store`, `cache\_size`, `journal\_mode`; `busy\_timeout` via the `Connection` method). The WAL-tuning PRAGMAs (`wal\_autocheckpoint`, `journal\_size\_limit`, `mmap\_size`) are no-ops in Turso and intentionally dropped. Add new PRAGMAs there.

\- Writes run on **single-writer WAL by default; MVCC is OFF**. `connect\_tuned` sets `journal\_mode='wal'` (and migrates files persisted as mvcc from the old default-on era; the wal -> mvcc -> wal round trip is a test). The seam keeps `BEGIN CONCURRENT` + conflict-retry so `FOXY\_DB\_MVCC=1` can opt in for experiments. Do not flip the default; the measured record is **WAL vs MVCC** below. Prefer plain `INTEGER PRIMARY KEY` over `AUTOINCREMENT` (rowid reuse is harmless for Foxy's keyed tables). Turso 0.7 allows only one in-flight write per connection: await writes sequentially on `OwnedDbTxn` / `copy\_table` / purge, and do not retry `SQL statements in progress` as lock Busy. A transaction that reads before its first write fails with `BusySnapshot` when another connection commits in between; the seam retries it like Busy (`DbErr` keeps it as `busy snapshot`, since Turso's text names neither), so such work must stay idempotent. Work that runs in parallel and often finds something to write should read outside a write transaction and write in single statements instead: the per-addon stale-link prune of the metadata rebuild did read-then-write, kept invalidating its siblings' snapshots, and failed silently before the retry existed.

\### WAL vs MVCC (Turso 0.7.2)

\- **Verdict: MVCC is worse for Foxy.** Leave WAL as the shipping journal. Engine microbenchmarks can look kind to MVCC; every real sync and purge we have measured is worse on `db\_write\_time\_ms`, and none of them is faster on wall clock. Re-open only after a Turso crate bump, then re-run the benches below **and** the same test-kit WAL vs MVCC pair.

\- **Stack that this record applies to:** Foxy 1.2.0, `turso = "0.7.2"` (`Cargo.toml` / lock checksum `f9491d7a...`), shipping write-gate 4, `FOXY\_DB\_MVCC` unset (WAL) vs `FOXY\_DB\_MVCC=1` (`journal\_mode='mvcc'` + `BEGIN CONCURRENT`). Compare only through `foxy-testkit compare` (never mix debug/release, GUI/CLI, or different gates). Cases: `perf-redownload-small-ssd` and `perf-redownload-big-ssd` on NVMe (GUI harness, 2026-09-09).

\- **Engine benches (0.7.2, `bench_mvcc_write_degradation` / `bench_mvcc_concurrent_writers`):** the 0.6 pathologies are gone (sequential upserts no longer degrade batch over batch; a 16-writer fan-out is ~7.7x *faster* than WAL at the engine). Write-gate 1 to 8: MVCC `db\_write\_time\_ms` stays flat (296 -> 426 ms) while WAL grows ~7x (300 -> 2 180 ms). Exclusive purge is still ~70% *slower* under MVCC (359 ms against 211 ms).

\- **Test kit, small redownload (217 files, warm n=2, gate 4):** force-redownload 51.17 s WAL vs 51.35 s MVCC (`no-difference`). `database.write\_time\_ms` 125 vs 210 (+68% candidate-worse). Recheck wall clock on this case is noise (WAL warm min 0.47 s / max 30.5 s vs MVCC ~0.44 s); do not treat that as an MVCC win.

\- **Test kit, big redownload (3738 files, ~92 GB, cold, gate 4):** 801 s WAL vs 805 s MVCC (`no-difference`, `compare` +0.22%). `database.write\_time\_ms` 11.6 s vs 37.4 s (+168%, about 3x candidate-worse). Recheck after a successful download is ~0.45 s on both. Download `elapsed\_s` is network-bound; a slower writer does not show up in wall clock until persistence is a large share of the run (refresh/purge, not a 92 GB transfer).

\- **How to re-measure:** `foxy-testkit run --case .\\testkit\\cases\\perf-redownload-small-ssd.json --database-mode wal --db-write-gate 4` then the same with `--database-mode mvcc`; repeat for `perf-redownload-big-ssd`; `foxy-testkit compare --case-id <id> --baseline wal --candidate mvcc --baseline-gate 4 --candidate-gate 4` (big cases are cold-only; pass `--cache-state cold`). Also re-run a real-sized exclusive purge. Isolated benches alone are not enough to flip the default.



\### Schema changes

Startup rebuild after an engine initialization failure is limited to structured
`turso::Error::Corrupt` and `NotAdb` errors. Other errors preserve the database
and propagate to the startup failure path; a failed bootstrap, file-access
error, or engine API change is not evidence that stored data should be reset.

\- Never edit `database.db` directly unless explicitly instructed.

\- The schema is a single folded bootstrap file, `sql/turso_schema.sql`, applied to a fresh database (no incremental migration replay; the legacy `migrations/*.sql` files are historical only). Edit that file for schema changes and keep its `ON DELETE CASCADE` chains and `(remote_url, local_path)` identity intact.

\- A change that an existing local database cannot keep using must bump `DB\_SCHEMA\_VERSION` in `tasks/db\_schema\_version.rs` by one. That triggers the startup wipe-and-rebuild prompt (the Turso cutover itself bumped 21 -> 22).

\- Update models and any query code that depends on the schema.

`storage_read_measurements` is an additive table applied by the bootstrap to
existing databases without a version bump. It stores a UTC-dated unbuffered
SSD read sample per opaque volume key in the active game-space DB. The live
wipe leaves it in place so a repository metadata rebuild can reuse a sample
younger than 30 days; replacing the database file loses it.

\### Repository instance identity is `(remote_url, local_path)`

\- A repository row is identified by the composite `(remote_url, local_path)`, not by URL alone (migration 21, `upsert_repository_entry` `on_conflict`). The same URL downloaded to two folders is two independent rows. `addons`/`files` are per-instance too: conflict-keyed on `(Name, RemotePath, LocalPath)`; `remote_files.rs` separates "matching remote paths but different local paths".

\- DELETE, purge and wipe operations target `(remote_url, local_path)`. Use `purge_repository_by_url_and_path`, `purge_repository_db_only_by_url_and_path` and `Foxy::wipe_repository_database_entries_by_url_and_path`. A `WHERE remote_url = ?` wipe destroys independent same-URL installations. Deleting an entry keeps shared or physically overlapping files and removes only its own database rows; an independent folder may have its managed files removed after confirmation. Changing a folder in Repository Settings scopes the old folder's rows the same way.

\- `pending_updates` is composite-keyed `(repository_url, local_path)`; read/write through `context.target_local_path`. Quick-scan expands each input URL to its DB instances (`load_repository_instance_paths`) and scans each with a path-scoped `FoxyContext`.

\- Cross-repo sibling checksum propagation (`tasks/calculate_hashes/propagation.rs`) joins on `source.local_path = sibling.local_path` (+ same `remote_checksum`) and only ever sets `local_checksum = remote_checksum` (marks synced, never unsynced). Whenever a tree checksum is copied, the sibling's `local_content_hash` baseline is copied with it (pre-propagation and post-hash propagation alike): a file marked synced without a baseline is skipped by the tree-hash init, reported as a content mismatch by the quick scan, and kept out of the download queue, which fails the sync with an empty queue. Standalone different-folder repos remain independent. The explicit exception is a repository-space member with its own override folder: manifest addons already present under that space's configured shared root resolve there, while addons absent from the shared root resolve under the member's override folder.

\- Matching an address from another source against added repositories (repository space entries, duplicate-add checks, Swifty imports) compares `repository_url_match_key` (`Foxy::repo_url_match_key`): the normalized URL, case-folded, because manifests are hand-written and hosts commonly serve paths case-insensitively. Never use that key for requests, stored keys, or event routing, which keep the configured spelling.

\- Every `local_path` used as a key must funnel through `content_hash::normalize_path` (idempotent) so core-emitted paths, the saved `pending_updates` key, and the UI's `repo.path` canonicalize identically.


\### Filesystem compatibility

\- `utils/storage_compat.rs` owns the filesystem rules: the family classification (`classify_filesystem_name`), the per-path volume probe (`VolumeProber`: `GetVolumePathNameW` + `GetVolumeInformationW` + `GetDriveTypeW` on Windows, the sysinfo mount table elsewhere), the role-based verdicts (`evaluate_volume`), and the per-file limits (`PathLimitReport`: FAT 4 GiB ceiling, Windows `MAX_PATH` including the `.foxy.part.meta.tmp` sidecar reserve, reserved names, case collisions). A mapped share reports the *remote* filesystem name, so `VolumeInfo::remote` (not the family) identifies network storage. Add a new filesystem or rule there, with a unit test; never string-match filesystem names at call sites.

\- The rules run in three places and must stay consistent: the startup diagnostics thread (`api/startup_diagnostics.rs`, volume verdicts plus one aggregate query per repository via `models/repository_limits.rs` for largest file and longest path), the download orchestrator gate next to the disk-space check (`check_destination_filesystem`, refuses before any file is written), and the direct-download worker. Blocking findings refuse the write; warnings are logged and surfaced once at startup through the UI "Storage check" notice (`foxy ui --debug-modal storage-check` previews it).

\- Keep the checks cheap: no tree load, no file reads, one probe per addon or path. The startup pass costs milliseconds and runs off the launch path; it must never gate the first frame.

\- Writability is tested by writing, not by reading metadata: `fs_safety::directory_is_writable` creates and removes a probe file, and `destination_is_writable` tests the nearest existing ancestor of a folder that does not exist yet. Windows ACLs and read-only mounts are invisible to metadata. Sync checks the repository folder and extra-file activation checks its destination this way before any write, and each reports an unwritable path through a toast instead of failing deep in a copy.

\- A force redownload (repository or addon, GUI and CLI) first probes the repository's `repo.json` with a bounded request and aborts with local files intact when it cannot be reached. Never purge or delete before that probe succeeds, and keep the addon probe off the UI thread.

\### Interrupted work and replaced files

\- Every replace of a repository file goes through the update rollback session. A target another process holds open without delete sharing (a running game keeps its PBOs open that way) refuses the rename aside, so the download orchestrator probes existing targets with delete access before the first transfer (`download_files::failure::find_targets_in_use`, re-probed once to skip brief antivirus holds) and refuses with `TargetsInUse`; a promote that still fails that way mid-transfer stops the run through `DownloadStop::target_held_open` and reports the same error after the rollback. Never retry such a file in place.

\- A rollback entry that was restored (a patch that failed verification, a promote retried after a failure) has consumed its `.foxy.bak` sidecar. The next replace of the same target registers it again with a fresh sidecar, and the journal's `Register` replaces the restored entry, so a later revert still has the original. Keep that guarded by `a_replace_after_a_restore_keeps_a_sidecar_for_the_final_revert`.

\- Delta-patch artifacts are named by database file id, so they live in a folder per game-space directory (`app_paths::foxy_patch_artifacts_dir`), and the pre-download cleanup keeps every artifact a `download_patch_file` row of this database still references; when the rows cannot be read it removes nothing. A shared folder let one space's download delete or reuse another space's plans, and a testkit run delete the live install's.

\- Startup recovery must leave the user's data where it was: a compaction swap interrupted between moving `database.db` aside and installing the compacted copy is undone from `database.db.bak` (`sweep_stale_db_artifacts`), and a live whole-database wipe writes the wipe marker before dropping tables and removes it on success, so a kill part-way finishes the wipe on the next start instead of opening a half-wiped database as healthy.

\- A configuration file that exists but cannot be read or parsed is copied to `<file>.unreadable` before anything can save over it (`fs_safety::preserve_unreadable_file`, `Foxy::report_unreadable_config`), and an unreadable `repository_spaces.json` skips the space-binding reconcile that would otherwise strip every repository's membership.

\- Closing the window while a sync worker runs cancels it and keeps the window open (`ViewportCommand::CancelClose`) until rollback and persistence finish. After 15 seconds offer explicit force quit with recovery information preserved; never force exit solely because that interval elapsed. No sync starts once close is requested.

#### Accepted recovery and retry contracts

- An ordinary close waits for the active sync to finish rollback before closing. If a force-quit choice is offered after a prolonged wait, it must say recovery is incomplete and retain enough journal state to finish recovery on the next start. Report unresolved recovery before treating that repository as ready.
- An unavoidable process loss recovers forward: keep promoted files, identify the interrupted repository instance, verify it, and offer to finish the current update. Do not report success or readiness until verification completes. A recorded user cancellation during ordinary close follows the restore contract above.
- Download Pause is durable intent scoped to the normalized `(remote_url, local_path)` instance within its game space. Closing cancels and restores active writes while retaining that paused intent. Startup shows pending work as paused; explicit Resume refreshes and validates the current plan before any transfer. Explicit CLI Download is also Resume for that instance; checks and dry runs retain the pause. Automatic, scheduled, queued, and bulk starts must not bypass the pause.
- A retryable terminal transfer failure may retry automatically while Foxy remains open when the app-global `retry_failed_downloads` option is enabled (default `true`). Show a countdown and Stop control, revalidate the plan each attempt, and retain the pending update on exhaustion. Explicit cancellation is terminal and never auto-retries. The option only controls retries after a terminal failure; it does not replace per-request retries.
- An update approval permits reaching the latest publication for the selected addons. Refresh and rebuild stale plans without a second confirmation solely because the byte estimate grew. Never use a stale plan or include addons outside the approved selection.
- A configuration file that cannot be read or parsed is preserved as `<file>.unreadable` before replacement. When preservation succeeds, ask for confirmation before the first save replaces that source. When it fails, block only writes that would overwrite that source until recovery is chosen. A backup is recovery evidence, not a repair.
- A corrupt database whose backup cannot be created may be discarded only after an explicit user choice that explains database metadata loss and distinguishes downloaded files and JSON configuration, which remain separate.
- An update that would install incompatible versions into a repository-space shared root is a conflict: block the update and identify the affected member repositories. For ordinary repository entries configured to share a folder, warn about affected repositories and let the requested update proceed; never mark incompatible siblings current.
- Launching while an update owns files needed by that installation queues a cancellable launch for that exact instance. Recheck readiness after the update completes. An update failure never launches automatically. Work in unrelated folders does not block the launch.

\### Processor use

\- Three app-global settings shape Foxy's CPU use and stay separate: **CPU Threads** (`utils/cpu_threads.rs`) is how wide CPU-bound fan-out and the sync runtime's tokio workers are planned, **Work priority** (`utils/work_priority.rs`) is who wins under contention, and the **CPU usage limit** (`utils/cpu_governor.rs`, default 90% of every detected thread, `None` for no limit) is how much of the computer Foxy may use on average. The limit is enforced in-process: the work threads measure process CPU (`thread_cpu::process_cpu`) every 100 ms, or 250 ms while pacing, and once the process reaches three quarters of the budget, each checkpoint books the CPU time its thread used since the last one (`thread_cpu::current_thread_cpu`) on one schedule shared by every work thread. The schedule advances at the budget minus the CPU the process spends outside checkpoints, and a thread waits until it catches up. Pacing the total, not each thread, is what holds hash pools far wider than the processor count, whose threads mostly wait on the disk: pausing one of them only lets another run. Both clocks come from `GetProcessTimes`/`GetThreadTimes` on Windows and `clock_gettime` with `CLOCK_PROCESS_CPUTIME_ID`/`CLOCK_THREAD_CPUTIME_ID` on Linux and macOS, so the limit holds on every platform; `cpu_governor`'s ignored `a_busy_process_settles_near_the_limit` and `a_wide_mostly_waiting_pool_settles_near_the_limit` tests prove it on the machine they run on. It is never a Windows job-object cap, which would also stall the UI thread at each quota interval and, without breakaway flags, cap the game Foxy launches.

\- `cpu_governor::checkpoint()` belongs between chunks of CPU-heavy work on a blocking thread (`spawn_blocking`, std threads): part hashing, whole-file hashing, BLAKE3 content hashing, patch copy runs and apply batches. Never call it on a tokio worker, and never while holding a lock, the Turso write gate or a transaction that other tasks wait on: it may sleep up to 1 s, in 50 ms slices that end early when the limit is lifted or pacing stops. With no limit it is one atomic load, and well under the limit it reads no thread clock. Each pipeline reports the limit and the time paused for it (`Pipeline CPU usage limit:` and `cpu_limit_percent` / `cpu_limit_paused_s` on `SOL op=sync_action`), so a slower run is attributable to the limit rather than to a regression.

\- Auto memory pressure (`utils/resource_profile.rs`), which narrows hashing and download concurrency, is classified from total and available physical memory only. Swap is logged (`swap_used=`) but never raises the tier: on Windows sysinfo reports commit charge beyond physical memory there, not pagefile use, and elsewhere swapped pages stay counted long after the pressure that pushed them out. A healthy 94 GiB Windows machine with 40 GiB free read 5 GiB of it and fell to the severe limits.

\### Process launching

On native Windows, Steam, TeamSpeak and Arma 3 running checks share the Toolhelp process snapshot helper in `utils/process.rs`, matching executable names exactly without case. Do not spawn `tasklist` for these probes. Steam registry queries use `CREATE_NO_WINDOW` so automatic detection cannot flash a console or steal focus. Wine keeps its native-host Steam detection path.

Windows in-app installers always receive `/MERGETASKS=!deleteuserdata`, including interactive and elevated launches, to clear a previous reset task while keeping shortcut preferences. The setup task uses `unchecked checkedonce`, and `CurPageChanged` explicitly deselects it whenever the task page opens, after Inno has restored prior choices and applied task presets. Deleting user data always requires ticking the checkbox in the current wizard. Its deletion handler refuses silent mode and requires a fresh confirmation with No as the default. An app update must never remove the Foxy data root or request a database wipe just to apply an installer fix.

Windows Foxy under Wine must use the native host Steam client when available. `core::steam::wine` detects Wine from the loaded `ntdll` export, maps native Steam roots and Linux `libraryfolders.vdf` paths through Wine's path APIs, reads the host `/proc` for Steam readiness, and uses the absolute Wine `start.exe /unix` bridge for native, Flatpak, or Snap launchers. Direct native Unix spawns have no Windows process handle, so callers must not rely on their PID or wait status. Arma launches append `-applaunch 107410`, skip the Arma launcher, and translate absolute mod/profile/mission paths to the target Proton prefix's host-root `Z:` drive. Keep the Windows Steam fallback and unelevated spawning intact.

\- Foxy does not request administrator rights (the installer is a per-user install and removes the old "Run as administrator" AppCompat flag), but a user can still start it elevated. A game started from an elevated Foxy inherits the admin token, and Windows then blocks unelevated Discord, TeamSpeak, and OBS from sending it input or capturing its window.

\- Start the game, Eden Editor, Steam, and any other user-facing child process through `utils::deelevate::spawn_unelevated`, which uses the shell's unelevated token when this process is elevated and falls back to a plain spawn (with a warning) when it cannot. It returns a raw pid. A bare `Command::spawn` for those processes is a bug.

\- The app updater checks `is_process_elevated` and the install folder's writability, and when replacing the binary needs elevation it starts the installer through `ShellExecuteW` with `runas`, so a declined UAC prompt is a real error instead of a silent no-op.

\- The global allocator is mimalloc (`src/main.rs`), committing pages on demand; it was chosen by measurement (`conventions/SPEED_OF_LIGHT.md`). Do not swap it without the same A/B.

D21 monitoring uses a retained bounded worker per owned run. Status carries only its optional BLAKE3 snapshot fingerprint; the 1024-byte result and 64KiB control frame bounds remain fixed. Snapshot readers authenticate status before and after a bounded cache read and verify the complete context/owner/run/activation identity and content hash. Query timeout is not process exit. Fresh matching local A2S establishes query readiness only; scenario readiness, joinability, backend registration and game FPS remain separate unknowns. CPU is percentage of one logical processor (may exceed100), RSS is bytes; neither estimates server FPS. Collection and query cancellation join with the retained run, without granting PID-only authority.
