# Testing conventions

## Validation strategy

The ignored `reforger::native_reforger_channels_install_and_maintain` case in `tests/server_native_install_cli.rs` requires `FOXY_REFORGER_INSTALL_ROOT` (an isolated existing registry containing a `reforger` space) and separate `FOXY_REFORGER_INSTALL_SCRATCH` (short ordinary Windows path, or user-owned mode0700 POSIX directory). It uses anonymous access unless `FOXY_REFORGER_INSTALL_ACCOUNT` names an already prepared session. Run `cargo test --locked -p Foxy --test server_native_install_cli reforger::native_reforger_channels_install_and_maintain -- --exact --ignored --nocapture --test-threads=1`. It downloads both channels, validates complete receipts/inventories, repairs a damaged private stable predecessor and updates experimental into fresh successors, preserving old bytes/operator markers/peer bindings and refusing cross-channel maintenance. Same-build reacquisition is not evidence of a historical upgrade. Keep all failed artifacts; provider/GUI cancellation and actual native copied-engine usability remain separate acceptance. This case never runs in ordinary tests or CI.

The ignored `native_reforger_addon_retained_lifecycle` case adds actual product addon acquisition before staging and committed lifecycle. Set `FOXY_REFORGER_ADDON_ID` and `FOXY_REFORGER_DEPENDENCY_ID` to explicit public test selections, optionally `FOXY_REFORGER_ADDON_VERSION` for an exact request, alongside the native source/scratch variables. It checks the retained dependency edge and versions, dry-run/yes gates, pinned runtime JSON and fresh native mounting of the pinned addon directories. Use a short Windows scratch root because cache-manifest filenames count toward the engine's existing path limit; do not relax that guard. `native_reforger_addon_acquisition` is a separate lower-level probe and does not replace product GUI/CLI acceptance. The ignored `native_reforger_resource_indexes_match_the_selected_resource_identity` unit case additionally takes `FOXY_REFORGER_NATIVE_ADDON` and `FOXY_REFORGER_NATIVE_SCENARIO` to check full native base/addon index parsing and exact scenario ownership. It proves index membership, not scenario execution. All remain excluded from normal tests and CI.

Reforger native acceptance is explicitly ignored in `tests/server_reforger_native.rs`. Set `FOXY_REFORGER_NATIVE_SOURCE` to a read-only dedicated installation and `FOXY_REFORGER_NATIVE_SCRATCH` to a separate ordinary private directory, then run `cargo test --locked -p Foxy --test server_reforger_native native_reforger_layout_isolation -- --exact --ignored --nocapture --test-threads=1` or `native_reforger_retained_owner_lifecycle` with the same flags. Linux execution requires an ordinary user and supported unprivileged containment. Layout proves three fresh engine/A2S generations, two mutable roots, observed private paths, retained marker and unchanged source/copy inventories. The CLI case adds reviewed committed activation and retained foreground lifecycle. Native process existence, listing output, requested directories and shutdown save messages remain separate from scenario readiness, addon acquisition and saved-game durability. Keep failed evidence and validate the exact current run's world/version/profile and A2S hostname. Windows Reforger uses its opt-in CTRL+BREAK helper on the controlled private console; Arma's default CTRL+C path stays unchanged.

- Start with targeted checks for the code you changed, then broaden to full checks before final handoff when feasible.
- Required final checks for code changes:
  - Format changed code without rewriting unrelated files.
  - `cargo clippy --locked --workspace --all-targets --all-features -- -D warnings`
  - `cargo test --locked --workspace`
- Run `cargo run` when the change affects UI startup, CLI behavior, app bootstrapping, or user-facing runtime flows. Skip it for docs-only changes and note that it was not needed.
- The tree has existing formatting differences. Do not run a blanket writing `cargo fmt` over it. Use editor formatting for the changed region, or `rustfmt --edition 2024 <changed-leaf.rs>` and inspect the diff. Formatting a file with module declarations may visit child modules, so check its scope first. `cargo fmt -- <files>` does not reliably restrict Cargo's file selection. A read-only `cargo fmt --all -- --check` is safe for reporting the workspace baseline; distinguish unrelated differences from changes introduced by the task.
- If clippy reports warnings, including pre-existing warnings in untouched files, resolve them when the fix is safe and straightforward (for example `collapsible_if`, `map_or` -> `is_none_or`, or `matches!`). Skip only when fixing would change semantics or require risky refactoring, and note that explicitly.

## Selecting checks

- During iteration, select the affected crate: `cargo check --locked -p Foxy --all-targets`, `cargo test --locked -p Foxy <filter>`, or the corresponding workspace package. A non-virtual workspace defaults to its root package, so an unqualified `cargo test` does not cover all members. Use `--workspace` at integration.
- Check that filtered tests actually ran. A test filter reduces execution, not package compilation; `cargo check` also does not verify linking or runtime behavior.
- For feature-dependent changes, test the affected feature explicitly or use `--all-features` when the combined set is valid. All-features checks do not exercise every feature combination or other platforms.
- Standalone helpers under `tools/` have separate workspaces and lockfiles. Use their `--manifest-path` commands in `tools/AGENTS.md`; root workspace checks do not cover them. For a standalone-only change, run those checks rather than rebuilding the application.
- For agent instructions, skills, loaders, and role changes, run `cargo agent-check` and `git diff --check`. The focused `Agent setup` CI workflow checks the helper and metadata without building Foxy. Documentation-only changes need no application build.
- Keep Cargo builds, Clippy, and tests sequential in the main agent so shared target directories are not contended. Do not run developer-machine testkit cases from unit tests, CI, or hooks.
- Batch a coherent change before rebuilding. Choose the next command for the missing evidence: a focused test already compiles its package, so a separate `cargo check` immediately before it is often redundant. Keep required final workspace checks after integration; repeat them after relevant source/build-input changes or a failure, not after private notes or documentation edits.
- Record the command, target/features, exit status, actual tests run and relevant source/environment inputs in the existing private task note. Reuse an earlier result only when those inputs and its acceptance scope still apply. Do not infer a current runtime or cross-platform pass from a warm build, old log, ignored result or aggregate count. Keep compile time, test execution and environment waiting separate when diagnosing slow delivery; do not promise a speedup without measurements.

## Behavioral evidence and expectation changes

Map each material changed behavior to the cheapest discriminating proof: pure logic at unit level, CLI/IPC/filesystem boundaries through integration tests, and native/platform/UI behavior through actual acceptance where required. Extend a useful existing case instead of duplicating its setup or asserting private implementation details. Test counts are diagnostics, not an acceptance target. [Milestone execution](../skills/foxy-milestone-execution/SKILL.md) supplies a compact mapping for multi-step work; [native acceptance](../skills/foxy-native-acceptance/SKILL.md) supplies preflight and evidence rules for external engines/processes.

Keep expected behavior grounded in a contract, known-good result or independently observed boundary. A test that generates both expected and actual values through the same helper cannot independently verify that helper. A regression should fail on the old behavior for the intended reason; when practical, verify this with a focused reversible negative control in isolated task-owned code. Source reasoning is useful but must not be reported as an executed before/after test.

Never delete/ignore a meaningful failing case, relax assertions, widen accepted versions, reuse stale output or extend timeouts merely to make a run pass. Fixture bugs can be corrected: preserve the failing observation, explain the independent evidence for the corrected expectation, and review the expectation change separately from the implementation. Add or retain a distinguishing negative case where useful. Do not turn a legitimate fixture correction into an automatic user-approval gate; product-scope changes still follow the user's instructions. Use [test oracle review](../skills/foxy-test-oracle-review/SKILL.md) for material expectation or acceptance changes.

See [Cargo package selection](https://doc.rust-lang.org/cargo/commands/cargo-check.html), [test selection](https://doc.rust-lang.org/cargo/commands/cargo-test.html), and [feature behavior](https://doc.rust-lang.org/cargo/reference/features.html).

The ignored `tests/server_native_install_cli/native.rs` case exercises native managed-install maintenance through the real CLI. Set `FOXY_NATIVE_MAINTENANCE_CONFIG` to an existing private config root with Arma space `alpha` and a prepared `default` Steam session, `FOXY_NATIVE_MAINTENANCE_SOURCE` to a complete managed native installation and `FOXY_NATIVE_MAINTENANCE_SCRATCH` to a separate existing ordinary directory. Run `cargo test --locked --test server_native_install_cli native_d16_managed_maintenance_preserves_shared_and_previous_installations -- --ignored --nocapture --test-threads=1`. It creates two fresh instance records in that acceptance config, copies the read-only source, validates, damages only the copy, performs actual repair/update downloads into fresh successors, and checks exact retained source/predecessor inventories and peer bindings. Per-step JSON stays in a fresh scratch child. Linux requires an ordinary user and scratch ownership/mode 0700 on POSIX storage. No credentials are copied. This downloads two full installations and never runs under ordinary tests or CI. A same-build native run proves reacquisition/publication; depot/build-change detection also needs focused selection tests. GUI review/cancel and CLI signal cancellation require separate observed evidence.

With the same inputs, `native_d16_physical_and_unresolved_gates_refuse_cli_maintenance` is a separate ignored native CLI gate case. It holds physical admission/runtime leases across another CLI process, exercises a pending supervisor maintenance intent and its exact aborted receipt, then retains an unresolved registration from an intentionally failed spawn. Apply must refuse each boundary without successor/staging writes. The fresh copied installation and unresolved evidence remain for inspection; this is gate acceptance, not a new game-engine lifecycle claim.

## Unit tests

`tests/server_steam_auth_cli.rs` contains the ignored native `native_windows_or_linux_account_login_and_prepared_reuse` fixture. Set `FOXY_NATIVE_STEAM_CREDENTIALS` to a protected local credentials file and `FOXY_NATIVE_STEAM_SCRATCH` to a separate private scratch directory, then run `cargo test --locked --test server_steam_auth_cli native_windows_or_linux_account_login_and_prepared_reuse -- --exact --ignored --nocapture --test-threads=1` on native Windows or Linux. It performs attended account login, starts a fresh CLI process to reuse the prepared token, then checks anonymous login and that a missing alias does not damage the saved record. Do not put credentials in the command line, tracked fixtures, or logs. The case is ignored in ordinary tests and is not a claim that D13 native acceptance has passed.

`tests/server_content_acquisition_cli.rs` covers offline plan and dry-run inventory preservation, exact review fingerprint and `--yes` gates, then an ignored native acquisition case. The ignored `native_repository_acquisition_patch_fallback_and_failed_generation_preservation` case requires `FOXY_REPOSITORY_PUBLISHER` pointing to the built `foxy-server-backend-cli` executable and may use `FOXY_ACQUISITION_SCRATCH` for separate scratch storage. Run it on native Windows and an ordinary Linux user session with supported containment: `cargo test --locked --test server_content_acquisition_cli native_repository_acquisition_patch_fallback_and_failed_generation_preservation -- --exact --ignored --nocapture --test-threads=1`. It checks a real local HTTP repository, private scratch DB, patch fallback, final stage bytes, and preservation of prior stages and source bytes after failure. The case is ignored in normal tests; compilation or a synthetic CLI test is not native acquisition acceptance. No D12 acceptance pass is claimed by the presence of this fixture.

The ignored `native_arma_mission_library_and_ordered_cycle` case in `tests/server_configuration_native.rs` uses `FOXY_ARMA_NATIVE_SOURCE` and separate private `FOXY_ARMA_MISSION_SCRATCH`. Run `cargo test --locked --test server_configuration_native native_arma_mission_library_and_ordered_cycle -- --exact --ignored --nocapture --test-threads=1` on native Windows and ordinary Linux. It imports real unpacked fixture missions, pins ordered enabled entries, stages/verifies exact PBO bytes, observes fresh Beta-to-Alpha engine mission progression, refreshes without retargeting the old pin, and explicitly rebinds a later committed generation. Keep source/adopted/predecessor hashes and retained lifecycle cleanup intact. Compilation and ignored workspace counts do not establish this acceptance.

`tests/server_configuration_native.rs` includes the ignored `native_arma_operator_import_configuration` case. Set `FOXY_ARMA_NATIVE_SOURCE` to a complete accepted native package and `FOXY_ARMA_IMPORT_SCRATCH` to separate private scratch, then run `cargo test --locked --test server_configuration_native native_arma_operator_import_configuration -- --exact --ignored --nocapture --test-threads=1`. Use short Windows paths and an ordinary Linux user on POSIX storage. It imports operator server/basic/profile files, extracts a synthetic credential, commits and activates the reviewed configuration, and observes two fresh native mission generations through the retained owner. It checks source/template preservation, private runtime credential materialization, retained namespaces and source/adopted payload hashes. It never runs from ordinary workspace tests or CI; compilation is not native acceptance.

`tests/server_activation_native.rs` is an opt-in native activation acceptance fixture. Set `FOXY_ARMA_NATIVE_SOURCE` to the accepted complete Arma dedicated package and `FOXY_ARMA_ACTIVATION_SCRATCH` to a separate private directory, then run `cargo test --locked --test server_activation_native native_activation_consumes_and_rolls_back_reviewed_generations -- --exact --ignored --nocapture --test-threads=1`. Use a short Windows scratch path and an ordinary Linux user on storage supporting POSIX modes. The fixture invokes the real CLI and authenticated owner to prepare, activate and roll back immutable runtime generations, then consumes their native launch plans through retained `ForegroundSession` containment. Exact mission/addon markers and namespace readback must come from each fresh engine generation. Source and predecessor payload hashes and mutable profile bytes are checked independently. It also interrupts retained non-game owner handles at intent, journal and pointer boundaries, resolves the exact observed transaction through a new owner, and verifies preservation before consuming the committed or predecessor runtime. Owner interruption never kills a game by PID. The Linux console helper is invoked only inside the retained native containment. These ignored fixtures never run from ordinary workspace tests or CI; compilation and synthetic tests are not native acceptance.

`tests/server_lifecycle_native.rs` is an opt-in native retained-owner lifecycle acceptance fixture, compiled only for x86_64 Windows or Linux. Set `FOXY_ARMA_NATIVE_SOURCE` to the accepted complete native installation and `FOXY_ARMA_LIFECYCLE_SCRATCH` to a separate private directory, then run `cargo test --locked --test server_lifecycle_native native_arma_retained_owner_lifecycle -- --exact --ignored --nocapture --test-threads=1`. Use a short Windows scratch path and, on Linux, an ordinary user on storage supporting POSIX modes. It exercises reviewed lifecycle requests through the retained foreground owner against successive real Arma runtime generations. The ignored fixture never runs in ordinary workspace tests or CI. Do not report D06 native acceptance as complete until the fixture has passed on both native Windows and ordinary Linux under these conditions.

`tests/server_reconciliation_native.rs` includes the ignored `native_arma_shared_consumers_pins_and_reconciliation` acceptance case. Set `FOXY_ARMA_NATIVE_SOURCE` to the complete accepted native Arma package, `FOXY_ARMA_KEY_SCRATCH` to separate private scratch, and `FOXY_ARMA_KEY_FIXTURES` to the fixture directory containing publicAlpha/publicBeta plus the signed PBO and matching `.bisign`. Run `cargo test --locked --test server_reconciliation_native native_arma_shared_consumers_pins_and_reconciliation -- --exact --ignored --nocapture --test-threads=1` on native Windows and ordinary-user Linux. It exercises two instances sharing an external source, pins retained generations, refuses reconciliation while a consumer runs, then reclaims only reviewed artifacts after that consumer stops while preserving source, peer-instance and operator data. Compilation, synthetic tests and ignored workspace counts are not native acceptance; do not claim a pass until this exact fixture succeeds on both platforms.

`tests/server_engine_native.rs` is an explicitly ignored real Arma engine observation probe. Set `FOXY_ARMA_NATIVE_SOURCE` to an existing complete native installation, `FOXY_ARMA_NATIVE_SCRATCH` to a separate private ordinary directory, and `FOXY_ARMA_NATIVE_LAYOUT` to `shared_222` or `isolated_legacy`, then run `cargo test --locked --test server_engine_native native_arma_layout_observation -- --ignored --nocapture --test-threads=1`. It copies and hashes selected payload files, retains foreground containment/consumer records, and runs separate loopback instances with synthetic mission/addon archives. Readiness requires exact mission/server identity and own-addon visibility with the other addon absent. A second contained process generation must read back both profile and mission-profile namespace values. A2S is recorded separately and is not a LAN mission-readiness gate. Each phase has a180-second deadline and forced waited teardown; complete layout/lifecycle, key trust and whole saved-game recovery are separate verdicts. Copies/logs remain in a fresh scratch child for inspection.

Optional `FOXY_ARMA_NATIVE_PREPARED` revalidates an existing shared-layout copy under the same private scratch, fills missing selected payload entries under an exclusive maintenance guard, preserves existing bytes and creates new run directories. Existing shared-runtime parent components must be ordinary directories. Linux copies include the executable's `linux64` loader dependencies and preserve execute permissions. Each instance receives separate scratch HOME/XDG paths, including a0700 runtime directory; scratch storage must support POSIX permissions. The ignored `native_engine_console_fixture` is launched only by the retained native parent inside its namespace and redirects the engine's console into fresh per-generation files. Never invoke it directly as a game launcher. Linux execution requires an ordinary user and accepting namespace policy; a compile or ignored result is not native evidence. Never execute adopted/source data or infer wider acceptance from these focused proofs.

Windows `native_arma_key_acceptance` is separately ignored and requires the same source/scratch/prepared inputs plus `FOXY_ARMA_NATIVE_SIGNING_TOOLS`, an ordinary directory holding installed vendor DSCreateKey/DSSignFile/DSCheckSignatures executables. It creates disposable fixture keys and a signed addon, uses a verified copied regular client with private profiles, and retains all engine sessions. A matching-key server must show the regular client's mission presence; a different-key server must emit explicit client rejection naming the fixture PBO. Missing presence or a timeout is not rejection. Headless clients are excluded from this proof because the engine exempts them from signature checks. The desktop client may require interaction; startup/lobby failures leave key acceptance unavailable and do not enable production lifecycle. Never run native probes from CI or ordinary workspace tests.

Optional `FOXY_ARMA_NATIVE_PUBLIC_KEYS` adds the disposable public fixtures `FoxyNativeAlpha.bikey` and `FoxyNativeBeta.bikey` to separate instance key directories. It enables Steam queries with `loopback = 0` while retaining `-ip=127.0.0.1`, verifies the nonce hostname through A2S_INFO, then strictly decodes bounded A2S_RULES/A3SB v3 signature records. Each engine must advertise its own key and the base `a3` key while excluding the peer key. Run this variant for both layouts and both native platforms before adding exact executable fingerprints to the compiled acceptance matrix. This proves engine key-directory selection, not regular-client signature admission. Optional Windows client profile seeds must be private, ordinary, bounded files below the same scratch, never live user profiles. The native probe always retains broader layout/lifecycle verdicts as false; its individual evidence must be reviewed with the supported-build boundary and production admission gates.

When a change adds or modifies a pure function, parser, helper, or self-contained algorithm in the core or CLI, add or update unit tests in the same file's `#[cfg(test)]` module. Be conservative and cover only the code you are actually changing:

- New non-trivial behavior: cover the success contract and a meaningful boundary or failure, reusing an existing focused case when appropriate. A function's visibility alone does not justify duplicate tests.
- Bug fix: add a regression test that fails without the fix.
- Changed function signature or behavior: update existing tests so they assert the new contract.

Do not add unit tests for trivial wrappers, logging-only code, UI draw functions, or code that only delegates to external I/O without local logic. Verify material user-visible or boundary behavior through integration/runtime checks; do not add redundant integration tests solely because a wrapper exists.

Existing test modules live inline next to the code they exercise. Follow the same pattern; do not create separate test files unless integration/E2E scope requires it.

`tests/server_durable_owner_native.rs` is ignored and requires an explicit private prepared `FOXY_DURABLE_CONFIG`, `FOXY_DURABLE_SPACE`, and `FOXY_DURABLE_INSTANCE`. Run `native_detached_owner_survives_controller_recreation --ignored --exact --nocapture` on native Windows and ordinary-user Linux for both Arma and Reforger. It requires no existing owner, starts a prepared detached supervisor through the actual captured-output CLI, observes fresh native query/resources/logs, waits past foreground grace, reconnects with identical owner/run/process identity, replays that run's completion, rejects another owner and active shutdown, then gracefully stops and verifies idle release. Check adopted executable size/BLAKE3 against the catalog before and after. Linux verifies the sampled game is a direct child of the retained namespace init; CLI clients stay in the ordinary user namespace. Failure cleanup uses authenticated exact scope and run only. A compile or ignored workspace count is not this native acceptance. Captured output must reach EOF while the detached owner remains live.

D21 extends both retained lifecycle fixtures with shared monitoring acceptance: exact current owner/run and hostname, fresh A2S, native game CPU/RSS/birth identity, bounded current-run logs and CLI snapshot parity. Linux separately verifies the sampled PID is the direct game child of the retained namespace-init PID. A loopback loss proxy must receive a genuine response from the actual configured engine before dropping it; shared query timeout is then checked beside an independently live retained process. This proves transport loss handling, not a native engine crash or game joinability. Failed artifacts remain in the private scratch config. The same source/scratch variables and ignored commands above apply.

The ignored tests in tests/server_monitoring_follow_cli.rs require explicit FOXY_MONITOR_FOLLOW_CONFIG, FOXY_MONITOR_FOLLOW_SPACE and FOXY_MONITOR_FOLLOW_INSTANCE. The plain follow case requires an already-running private owned instance; it reads at least three real NDJSON frames, delivers retained Ctrl+Break on Windows or pidfd-bound SIGINT on Linux to that CLI child, verifies one cancelled end frame and unchanged server identity/process presence, and retains bounded evidence. Linux runs this client in the owner's ordinary user namespace; game containment would change its identity and correctly fail protected handoff access. The private Reforger owner lifecycle wrapper reuses a prepared private config, starts its own parent-bound owner and reviewed committed runtime, runs that same assertion, then separately verifies graceful fixture teardown. Neither case runs from ordinary cargo test or CI. No arbitrary PID signal or shared-desktop console event is permitted.
