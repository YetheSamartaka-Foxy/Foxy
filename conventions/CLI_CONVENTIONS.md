# CLI conventions

`server publish plan|apply|verify` reads the selected committed record in the captured game space. Plan and `apply --dry-run` are write-free. Apply requires `--yes` and the exact plan fingerprint, stages alongside the new absolute output folder, verifies the staged output, and atomically refuses replacement. Read-only Verify accepts an optional fingerprint. JSON reports the source record, selection or verification and explicit write/DB flags. Keep all paths offline and refuse database wipe.

`server service export` uses the native host format and a captured game space. No output path or `--dry-run` is a write-free preview. An output path saves a new definition atomically and refuses overwrite. JSON includes the complete reviewed definition, literal argv, fingerprint and explicit write/registration flags. Export opens no database, contacts no owner and performs no registration. `server supervise --background` is Windows console suppression for a foreground owner. `server owner --app-update-check` includes the shared config-root update barrier alongside the authenticated owner observation.

`server admin` exposes typed native Arma commands. Mutations require `--yes` and an explicit expected run generation; dry-run stays owner/write-free. Preserve raw replies with an explicit incomplete verdict when native list parsing fails. Exit0 is transport reply, exit5 is unknown/incomplete, exit4 is refused/not sent, exit2 is validation. Never report an empty acknowledgement as completed administration. Maintenance Arma hooks preserve job revision and once-only occurrence identity; backup requirements remain blocked until implemented.

`server reforger-admin players|bans|kick|ban|remove-ban|reload-scenario|logout` routes typed native Reforger commands through the existing owner and retained command ledger. Side effects require `--yes` and `--expected-run-generation`; dry-run contacts no owner. Player and ban lists expose completeness plus the bounded captured transcript, and an incomplete/empty acknowledgement is not a verified empty list or completed effect. Ban identity validation currently accepts only the conservative observed 44-character Base64 form; this remains provisional. Do not infer pagination totals or retry an unknown command. `reload-scenario` is a lifecycle operation that verifies fresh scenario/world evidence and a later query within the same process run. See [Reforger administration](../wiki/Server-Reforger-Administration.md).

Durable server ownership is explicit: `server supervise --detach --yes` and reviewed `server instance start <id> --detach --yes` establish or promote one prepared owner through an authenticated launch/scope handshake. Repeating detach preserves that owner and its runs. `server supervise --shutdown --yes` refuses active sessions or operations and verifies game-space release before reporting it. Both lifetime previews are owner/network/write-free. `server owner --events-after N` returns the current authenticated owner and at most eight generation-scoped retained events, with gap/head/earliest metadata; a new owner generation resets history. IPC clients never open Turso or gain PID-only authority. Terminal foreground ownership cannot be silently abandoned.

Native `server installation install|update|repair plan|apply` accepts optional `--channel stable|experimental`. Fresh Install defaults stable; Update/Repair default to the installed channel and reject explicit changes before contacting Steam. `--branch` remains a branch within the selected app. Reforger channels use independent dedicated apps and new destination folders; Arma's Experimental channel choice is unsupported. Check uses the receipt channel and Validate stays offline. Preserve exact review fingerprint, `--yes`, `--dry-run`, JSON and joined cancellation. Verified package integrity grants no new runtime compatibility or implicit restart.

Exact native Reforger `1.9.0.37` layouts on Windows/Linux x64 use the shared `server deploy activation` and `server instance start-plan|start|status|stop|restart` operations. Preserve the existing review fingerprint, generation, `--yes`, `--dry-run`, stable JSON and retained-owner contracts. Activation requires explicit typed `bind_address`, distinct game/A2S ports and a saved scenario. Addon-bearing inputs additionally require an exact verified staged addon lock. `server reforger-addons list|plan|acquire` uses a separate isolated vendor-engine session and immutable per-instance revisions; acquisition requires `--yes` and the reviewed fingerprint. An omitted desired version stays latest intent, while runtime JSON pins every realized version and omits unavailable optional rows. A degraded acquisition returns exit5. Unsupported hashes/channels, incomplete dependencies, unknown scenario ownership and stale intent refuse. Native depot installation remains separate. See [Reforger lifecycle](../wiki/Server-Admin-Guide.md#reforger-native-adoption-and-foreground-lifecycle).

`server mission` lists, reviews/imports, refreshes and directly acquires Arma mission library revisions; `cycle` reads or replaces the typed ordered cycle through the revision-checked shared draft store. Apply requires `--apply --yes`. Source files remain read-only, and library refresh never retargets an existing pin. Acquisition review uses temporary downloads and reports `downloads_started`/`temporary_download` separately from persistent `writes_performed`; acquisition dry-run validates inputs without network, temp files, owner or DB claims. Read-only commands keep the metadata CLI startup exemption. Operator-owned server configuration prevents structured cycle replacement. See [missions](../wiki/Arma-Server-Missions.md).

`server configuration import` reviews bounded Arma server/basic/profile files with operator ownership by default; `--managed` explicitly converts supported fields. Preview is write-free and redacts secret values. Apply requires `--apply --yes`, the captured revision and unchanged source bytes. Unresolved paths may be saved for later review but block activation until explicitly acknowledged with `--review-paths`. `export-pack` creates a new standalone `.foxyserver` file without overwriting; `import-pack` uses the same review/apply contract to create a fresh unbound draft. Packs retain credential references and unresolved source intent, never credential values or installation authority. These files are distinct from client `.foxypack` packs. See [configuration import](../wiki/Server-Configuration-Import.md).

`server configuration import-reforger <id> --expected-revision <n> --file <server.json>` reviews a Reforger server.json without writing. `--apply --yes` replaces that draft and bumps its revision. `export-reforger <id> --file <new.json>` writes the saved draft, including preserved unknown fields, and refuses an existing destination. Password, secret and token values are removed rather than stored. `scenario parse-log --file <log>` is write-free and does not select a scenario. `scenario import-log <id> --file <log> --yes` stores only a complete official listing and leaves the selected scenario unchanged; a failed parse writes nothing. `scenario list <id>` reports whether the selected resource is in the stored listing. `--dry-run` previews the mutating commands without writing. A listed or typed resource name does not prove the scenario file exists. Arma cfg import remains unavailable for Reforger.

`server installation inspect` preserves `data.installation` and adds ephemeral `data.build_observation`: bounded Windows ProductVersion metadata and an exactly matched local Arma Steam manifest. Empty explicit BetaKey maps to public; absence/conflict remains unknown. Never infer a branch from another library or nested KeyValues object, execute a version probe, cache this in the catalog, or promote observation to layout/authenticity/package authority. `build_version_verified` remains false; inspection/dry-run remain write/owner/DB-free.

For the offline server metadata commands below, a captured-space claim means either the retained local claim or the authenticated serialized metadata permit described in the foreground ownership section. Both retain authority through worker cleanup; neither permits Turso access or lifecycle execution.

Server installation consumer inspection adds a shared `recovery_inspection` beside the preserved `consumer_inspection`. Both come from one captured core report; preflight exposes the same recovery object. Pending is an explicit inspected status, not an operation failure or a readiness claim. Incomplete physical/local metadata inspection returns a completed envelope with exit4; preflight preserves exit0 blocker semantics. Reports are DB-free, write-free and lease-free, retain wipe refusal and remain usable beside an owner. History summaries are bounded and truncation explicit. No clear/force/resolve action is introduced by inspection.

- Core idea: if a user can perform an operational action in UI, they should usually be able to perform it via CLI too.
- Be conservative when extending CLI: add commands for deterministic, scriptable, automation-friendly operations first; avoid purely visual/UI-only controls or highly interactive flows.
- When adding a new app capability, explicitly consider CLI parity in the same change.
- If CLI parity is in scope, add or extend CLI commands and output for it.
- If CLI parity is not in scope, include a short rationale in change notes explaining why it is deferred.
- Keep UI and CLI behavior aligned by reusing shared core/domain logic instead of duplicating business rules.
- Preserve automation guarantees in CLI output and behavior.
- `foxy ui --mode client|server` overrides presentation for one UI session; keep it separate from persisted settings. `foxy settings set --app-mode client|server` saves the app-global preference, defaulting to Client. Other CLI commands never consult this preference. Server mode exposes typed desktop instance drafts with independent navigation and reviewed native Arma activation/recovery; exact native Arma runtimes also have separate owner-routed foreground lifecycle controls.
- `--json` output should remain machine-readable and stable.
- Destructive actions should require `--yes`.
- Exit codes are stable: `0` success, `2` validation, `3` not found, `4` operation failed, `5` partial success, `6` database busy. `6` means another Foxy process owns the game space database (Turso has no multi-process access); it is distinct from `4` so scripts can retry once the GUI is closed rather than treating it as a real failure.
- Support `--dry-run` where feasible.
- CLI must operate on the same config/data root as UI (app-global `app_settings.json`/`games.json`/`window_state.json`, plus per-game-space `game_settings.json`/`repositories.json`/`repository_spaces.json`/`database.db` under `games/<space_id>/`) and honor `--config-dir`.
- Per-game-space files resolve from the active game space in `games.json`. `foxy game list|use|create|remove` manages game spaces; `game use` takes effect immediately for subsequent CLI commands and on the next UI start. `game remove` is destructive and requires `--yes`.
- `foxy game launch` is the repository-free launcher for active generic game spaces. For `twwh3`, it reads enabled managed Workshop items, writes `used_mods.txt`/`my_mods.txt`, then launches with the generated manifest argument. Without `--execute`, or with global `--dry-run`, it must only preview the command and manifest.
- Launches report a successful command handoff, not proof that the game started or a server connection completed. GUI Launch/Join requests queued behind an update belong to one repository instance: changing the requested action requires confirmation and readiness is checked again for the final choice.
- Executed launches for games with a Steam App ID require Steam to be running immediately before dispatch, including after automatic startup. A missing launcher or exited client is an operation failure, never a direct-launch fallback. Generic games without a Steam App ID skip Steam preparation and report `steam_status: "not_required"`.
- Steam Workshop management is per active game space through `foxy workshop list|add|import|remove|unsubscribe|set|order|freeze|unfreeze|export|share|checksum|bundle|resolve`. `remove` unregisters the item and can delete its private frozen copy; it does not unsubscribe or delete shared live Steam content. `unsubscribe` is a separate Steam action. Network or Steam-touching paths support explicit backend selection (`steam-helper`, `steamcmd`, or `none`) and destructive removal keeps `--yes`.
- `foxy workshop share` prints the pipe-separated share code and `foxy workshop import` accepts one, so a pasted list from another player or mod manager round-trips. `foxy workshop bundle export|inspect|import` moves the same selection plus the frozen mod files as a `.foxyshare` zip; import previews selection changes and supports `--mode merge` (keep unlisted items) or `--mode match` (disable unlisted items without deleting their payloads). Import is destructive and keeps `--yes`.
- `foxy workshop freeze --all` pins every managed mod in one pass (`--refresh` moves existing pins onto the current build), and `foxy workshop pins` reports which pins have drifted from Steam, exiting `PARTIAL_SUCCESS` when any has.
- `freeze --all --refresh` stages all requested snapshots and commits the active pin selection once; any snapshot or final-save failure retains the previous selection.
- `foxy workshop checksum` prints the shareable state code, and `--compare <file>` diffs it against another player's `--json` output, exiting `PARTIAL_SUCCESS` when the two states differ.
- `foxy game reforger list|add|import|remove|set|freeze|unfreeze|export|resolve` manages the Arma Reforger GUID addon store (`reforger_addons.json`) of the active space; it has no desktop UI yet.
- `foxy config export <file>` / `foxy config import <file>` write and read `.foxypack` config packs. Import applies config and payload changes as a recoverable unit, retaining exact-space recovery intent until final saves complete. `foxy config extra-file list|add|remove|set|activate` manages extra files. Both are CLI-only for now, so the README roadmap and the user guide must say so until a UI exists.
- Extra-file `--order` is zero-based and can change without changing enablement. Activation dry runs expose destination conflicts, ordered winners and required review. Changed destinations require per-id Keep/Reapply; overwrite and layer approval retain `--yes`. Launch previews expose `extra_file_preparation` with the same read-only evidence, and execution binds layer approval to the inspected signature. Import preserves incoming extra-file order.
- Operational commands claim the configuration root before shared state reads or migration; a second owner exits `DATABASE_BUSY=6`, including a command targeting another space. Explicit integration helpers remain exempt. Device changes behind the same update path fail closed in CLI sync; review and approve the current target in the GUI before retrying. Checks remain read-only with respect to destination payloads.
- `foxy game remove <id>` requires `--yes`. If the space has private frozen Workshop or extra-file payloads, it also requires exactly one of `--preserve-payloads` or `--discard-payloads`; `--dry-run` previews these payloads and the required choice.
- `foxy direct-download` previews destination collisions and only replaces them with both `--overwrite` and `--yes`. It stages replacements so failed or cancelled transfers keep old complete files, leaves unrelated files alone, and refuses overlap with managed installations.
- Backup restore prefers matching game-space and repository-instance origins; cross-origin or unknown legacy backups require review and consent. Cleanup previews its deletion set and needs a separate approval before deleting a final recovery copy.
- `foxy repo force-redownload` and `foxy addon force-redownload` probe the repository before deleting anything and fail with local files intact when it is unreachable, matching the GUI.
- `foxy repo wipe-db` and `foxy repo force-redownload` act on the selected repository's folder only, like the GUI: another folder's copy of the same address keeps its records. Never purge by address alone from the CLI.
- Repository removal and content deletion must identify the selected `(remote_url, local_path)` instance. Preview and remove only its physically owned files; same-address installations in other folders retain their bytes and state.
- `foxy server inspect-addons` queries a live Arma 3 server's addon list through the Steam rules protocol; it does not open the database and may run beside the GUI.
- `foxy server context [--game-space <id>]` captures an immutable existing root/space/game context through `core::server::ServerContext`. Dispatch before layout preparation, logger initialization and schema hints. It never creates directories, migrates/repairs a registry, claims or opens a DB, or remembers the selector. Missing/invalid configuration is a validation error. Reject `--wipe-db` before claiming the config root, including when no selector is given.
- `server capabilities` and `server instance list|show|add|clone|rename|replace|validate|remove` use the same early captured-context route. Instance inspection, validation and dry runs are write-free. Mutations plan first, retain a local captured-space claim or authenticated metadata permit, then apply an optimistic catalog revision/fingerprint check through `core::server::ServerStore`, without opening Turso or changing the remembered selection. Edit/clone/remove require `--expected-revision`; removal requires `--yes` unless dry-run. These commands always reject `--wipe-db`, including without a selector. `replace --file` accepts the typed `data.instance` document, never a vendor config or the whole CLI envelope. Draft validation does not imply deployment readiness. Desktop forms reuse the same store operations through the Server owner permit; a client GUI claim or competing metadata operation returns busy.
- Database-using CLI commands prepare the remembered game-space layout before their ownership claim. The dispatcher must not reseed selection afterward. Only `LockOutcome::Acquired` permits dispatch; Busy is code `6`, Unavailable is code `4`. Resume the DB admission gate explicitly after a successful claim. Schema hints run only for DB-using commands.
- `server installation list|inspect --directory` and instance `adopt|bind|preflight|render` use the same early DB-free captured route. Adoption binds observed native executable evidence under a revision check; Bind reuses or clears a recorded identity. Read-only inspections, preflight, rendering and dry runs never claim or write. Mutations recheck evidence and exact source state under the existing claim. Catalog migration previews include the exact v1 backup effect. All management leaves reject `--wipe-db` before bootstrap.
- `server configuration plan|list|commit|verify|rollback` manage configuration-only snapshots, independently of draft saves and runtime deployment. Commit requires the reviewed draft revision, configuration generation and renderer fingerprint. Rollback requires expected generation and `--yes` except in dry-run. JSON/TOON keep the normal envelope. Verify returns a structured report with `ok: true` and exit `4` when inspection completes but integrity is invalid; automation checks `data.verification.valid`. Missing/invalid input remains `CommandError` with null data. Preflight similarly returns completed report success while readiness is false. Neither config selection nor rollback changes a game process, installation, draft or save.
- Capabilities derives availability from `core::server::support_report` and adds `runtime_prerequisites` without changing existing envelope/availability keys. Instance preflight includes the same prerequisites plus selected configuration generation/integrity/current-draft comparison and bound installation consumer inspection. Invalid/unreadable configuration or consumer metadata is a completed preflight blocker, not a successful deployment. Read-only inspection never creates the installation lease registry or acquires a lease. Elevated/unknown Windows owners, privileged Linux owners and unavailable Linux namespace APIs fail closed for process execution; lifecycle needs a separate verified native Start review; start previews remain read-only.
- `server installation consumers <installation-id> [--game-space <id>]` reads the same core consumer inspection without a DB claim, database open, writes or liveness probe. The existing JSON/TOON envelope contains `data.consumer_inspection`; complete empty/nonempty inventory returns exit 0, completed unknown inspection returns an `ok: true` report with exit 4. Missing installation returns 3 and invalid ID returns 2. `cleanup_required` is null when unknown. Liveness and maintenance authorization are always false. Preserve the ordinary preflight exit-0 blocker convention and existing `--wipe-db` rejection. No clear/force/reconcile mutation is exposed.
- `server content` uses the same early captured-context dispatch as the other management leaves. Inspection and dry runs do not initialize logging or create config-root locks. Reject `--wipe-db` before bootstrap or ownership claims.
- `server content plan <instance-id> --bindings <file>` consumes a bounded JSON array of `{source_id, role, order}` where source_id names a saved profile. It captures instance/catalog revisions and the raw source-registry fingerprint, sorts roles/order independently of client state and returns a completed report under `data.plan`. Completed blockers retain exit 0 and `deployment_ready: false`; malformed/stale requests use 2, missing instances 3, and storage failures 4. Optional `--expected-revision` and `--expected-sources-fingerprint` refuse changed review inputs. No runtime paths, locks, database, logs, copies or network work are created; `--dry-run` is identical. Actual source registration claims only the captured space, pins that claim through synchronized atomic replacement and rechecks its expected raw fingerprint. Busy remains code 6. Local-only profiles use empty URL with already-present supply; no implicit acquisition fallback.
- `server content bindings show|plan|save <instance-id>` manages the separate schema-v1 instance-owned selection. Show returns `data.state` with optional document/raw fingerprint, `review_current` and issues. Plan consumes the same `--bindings` array and returns `data.plan.document`, directory `preview`, `expected_generation` and its own save `fingerprint`. Save requires `--expected-plan-fingerprint`, reconstructs exactly that review, then pins the captured space claim and rechecks before replacing the owned intent file. Wrong/stale review inputs use 2, missing instance 3, corrupt/future/unsafe storage 4, and Busy 6. Show/plan/save --dry-run remain logger/lock/DB/write-free. Actual saves may create claim artifacts and ordinary binding parent folders, but never open Turso or mutate client/source/catalog/content bytes. No --yes is required for this configuration save. An empty reviewed array clears selection through a new generation without deleting content. A saved source/catalog fingerprint is review evidence, not byte integrity, activation or launch authority. All content leaves retain early --wipe-db refusal and JSON/TOON contracts.
- `server content stage plan|apply|verify|list <instance-id>` hashes and retains immutable, unselected local content stages from the current saved binding document. Plan may require `--expected-bindings-fingerprint`; apply requires `--expected-plan-fingerprint` from the exact plan and can also require the binding fingerprint. Apply `--dry-run` rebuilds the plan and verifies both fingerprints without files or a space claim. Only a real apply claims the captured game space, pins ownership through publication and creates a stage; no stage command opens Turso. Verify checks the retained schema-v1 manifest and exact directory/file hashes without relying on current source bytes. List is read-only inventory only and never proves integrity. Ctrl+C requests cooperative cancellation for plan/apply/verify; the CLI joins the worker and waits for owned temporary cleanup before returning operation-failed (4). Previously published stages remain intact. Staging itself does not download content, activate a deployment, or establish engine readiness. Native Windows/Linux Arma activation acceptance covers use of local stages, not provider acquisition or general server readiness. Keep the normal JSON/TOON envelope and `--wipe-db` refusal.
- `server content acquire plan|apply <instance-id> [--seed-stage <id>] [--expected-bindings-fingerprint <hash>]` reviews/downloads selected saved download profiles. Plan is offline, write-free, DB-free and makes no HTTP requests. Apply requires `--expected-plan-fingerprint`; a real apply also requires `--yes`, while global `--dry-run` checks the exact review without network, writes, or opening a database. Apply resolves the current publication when it starts, then uses a private contained sync child and scratch database per profile; it never opens the live client database. A matching verified seed stage is copied into scratch and normal patch-first sync/full-file fallback and final verification run before publishing one inactive retained stage. Repository identity remains `(original URL, local path)` and source folders, client enablement and active deployment are unchanged. Overall incomplete/failed/cancelled results are returned as `ok: true` structured outcomes with exit 4 when operation execution completed; inspect `data.outcome.status` and per-profile results rather than treating envelope `ok` as successful acquisition. If failure occurs before an outcome can be assembled, ordinary CLI error handling applies. Unwitnessed helper failures serialize `downloads_started` or `scratch_database_opened` as `null`; cleanup failures are reported and retained/unknown scratch is not pruned. This path does not claim native provider, Steam depot or Workshop acquisition. Preserve JSON/TOON envelopes and early `--wipe-db` refusal.
- `server deploy prepare|commit|list|verify` manages offline deployment records. Prepare/commit use the persisted active configuration and explicit stage ID. Expected instance/configuration/deployment generations are optimistic guards; commit also requires the exact fingerprint returned by prepare and recomputes the plan. `list` is only an ID inventory; `verify` checks the retained record and referenced archives. Only an actual commit claims the captured space; none opens Turso. Records pin immutable archives by identity and hash, do not copy them, and never activate runtime deployment. `--dry-run` commit is read-only; all deploy commands reject `--wipe-db`.
- `server deploy runtime plan|build|list|verify` prepares an immutable, unactivated copy of the currently selected indexed deployment record. `plan` and `build` require the instance ID and `--expected-deployment-generation`; `build` also requires `--expected-plan-fingerprint` from the plan. `verify` takes the instance ID and explicit preparation ID. Plan/build verify the indexed record and pinned configuration/content archives, independent of today's draft, source registry or configuration selection. Build copies full archives to `deployments/prepared/prepared_<hash>/`; only an actual build claims its captured game space, and none opens Turso. Plan/list/verify and build `--dry-run` are read-only and safe beside a busy DB owner. Listing reports IDs only, not integrity. Preparation verification uses the copied manifest and bytes and does not require original archives, while still requiring a valid current context and instance. No `--yes` is needed because build adds an immutable offline generation; it changes no selection, active deployment, runtime, process, lease, consumer or provider state. It never cleans up other entries. All commands reject `--wipe-db` and preserve the standard JSON envelope and busy/error codes.
- `server deploy activation plan|apply|status|recovery-plan|resolve` implements exact-layout native Arma runtime activation and transaction recovery without starting the engine. Native Windows and WSL acceptance passed for the tested Arma 2.22.154089 layout and scenarios; this does not establish general platform release or engine readiness. Plan takes `<instance-id> <preparation-id> --expected-deployment-generation N --expected-activation-generation N` and returns the fingerprint-bound payload review. Apply repeats those inputs plus `--expected-plan-fingerprint`; real apply requires `--yes`, while global `--dry-run` checks the exact review without starting an owner or writing. Status verifies the active private runtime. Recovery-plan reviews retained transaction state; resolve requires its exact `--expected-plan-fingerprint` and `--yes` except for dry-run. Actual Apply/Resolve start or attach to the authenticated foreground metadata owner and use protocol-5 deployment operations plus installation admission, without opening Turso. Attached owners are not stopped by the CLI. Uncertain owner/transport outcomes are unknown delivery: inspect status and obtain a fresh recovery-plan before considering Resolve; never retry as a new activation effect based on timeout alone. The complete private copy leaves the adopted installation and preparation source unchanged. Scope is the exact tested Arma 2.22.154089 layout on Windows/Linux x64, selected base files, saved configuration, mission templates, server-only addons and unchanged base `a3` key; extra/changed keys and client-required/optional addon trust are rejected. Per-instance profile/config/cache/runtime state stays mutable and separate. Dedicated lifecycle is a separate owner-routed operation; broader trust remains unavailable. All commands reject `--wipe-db` and preserve JSON/TOON envelopes and stable error codes.
- `server content consumers` reports source/repository identity and instance use. Source discovery is limited to game spaces in the same config root; physical-installation consumer registrations are shared across roots. Keep private stages and runtime copies out of external source folders; intentional sharing uses an external content root.
- `server deploy pins|pin|unpin` uses expected pin generations. Pin validates the indexed record; unpin accepts a syntactically valid ID without requiring the record to exist, and never deletes records or artifacts. Mutations require `--yes`; dry-run validates admission and writes nothing.
- `server deploy reconcile plan|apply` reports retained/candidate artifacts and blockers. Apply requires the exact plan fingerprint and `--yes`; it refuses live or uncertain instance consumers, requires full manifest/hash ownership and scoped durable receipts for interrupted quarantine removal, and never opens Turso, routes to `--wipe-db`, or retires consumer registrations. Preserve the JSON/TOON envelope and stable error codes.
- `server deploy select-plan <id> <record-id> --expected-deployment-generation N` reviews an indexed record and verifies both referenced archives. `select` takes the same target/generation plus `--expected-plan-fingerprint`; every non-dry-run invocation requires `--yes`, while `--dry-run` exempts it. Both are database-free; only actual select claims the captured space and updates the existing offline state file. Raw state and plan fingerprints reject stale reviews. Selection never creates/deletes archives or depends on today's draft/source/configuration intent; a no-op leaves the generation unchanged. Invalid/stale/required-yes errors use 2, missing/unindexed uses 3, storage/future-schema errors use 4, and Busy uses 6. Preserve early `--wipe-db` refusal and JSON/TOON output.
- `server deploy plan <id> [--stage ID] [--expected-revision N] [--expected-configuration-generation N] [--game-space ID]` returns a completed read-only composition report under `data.plan`. The stage selector is optional but exact: omission yields a missing-stage blocker, never a latest-stage guess. Configuration evidence uses the persisted active selection, not a UI history highlight. Expected revision/generation mismatches are validation errors (2); a missing instance is 3; corrupt catalog, saved selection/binding state, unsupported versions in those stores, and storage failures are operation failures (4). A corrupt or unsupported selected configuration/content archive is retained as a completed blocker with exit 0 when the report can be assembled. `--dry-run` is the same plan. This dispatch rejects `--wipe-db`, does not initialize logs, prepare/migrate the root, claim or open the DB, write files, access the network, or rehash an adopted executable, and may run while the game-space DB is busy. Its deterministic fingerprint identifies the report only and grants no apply authority. JSON/TOON retain the usual envelope; completed blockers remain `ok: true`. Native Windows/Linux capability does not establish Linux integration acceptance, provider acquisition, server engines or detached ownership.
- User-visible command, flag, or exit-code changes update the CLI tables in `README.md` and `wiki/User-Guide.md` (client) or `wiki/Server-Admin-Guide.md` (server) in the same change.

## Native Steam session commands

`server session list|plan|apply <instance-id>` is Reforger-only local metadata, with no Turso access. Plans bind the inventory generation, complete native savepoint bytes and metadata UUIDs, active deployment and exact intent. Apply requires stopped verified writers, `--expected-generation`, `--expected-plan-fingerprint` and `--yes`; dry run has no write or owner claim. The four modes are configured, latest, selected (`--save-id`) and new. This records next-launch intent; it never requests a save or starts a process. Automatic selection rejects unknown/incompatible saves and custom/shared provider overrides instead of falling back to a fresh session. Configured preserves custom-provider configuration without claiming local inventory or recovery coverage.

`server steam status|login|resume|anonymous|forget` operates on the captured game's separate protected Steam session store; it never opens Turso and rejects `--wipe-db`. Alias defaults to `default` and is not an account name. Status inspects local record presence without network access. Resume is unattended and token-only; rejected credentials preserve the record and report `AuthenticationRequired`. Password login reads bounded private JSON from guarded stdin or a protected credentials file, and Guard codes use private input. Never accept passwords, tokens or codes in argv or include them in output/logs. Global `--dry-run` may inspect the alias, but does not request credentials, read a credential input file, contact Steam or write. Forget requires `--yes` except during dry-run. JSON result data stays on stdout and prompts/phases on stderr. Exit 2 is invalid input, 4 is auth/network/storage failure, and 6 is a busy store; preserve the fixed `AuthError` category in structured output. `credentials_saved` is `null` after a post-commit `StorageUncertain` result. Native CM authentication is disconnected before return; it prepares/validates a session but does not acquire depots or Workshop items. The per-space token store is independent from SteamCMD cache and never logs out or resets it.

`server installation install plan|apply` is the native provider install path. Plan contacts Steam read-only (PICS app info and depot-key entitlement), writes nothing and opens no database; apply requires `--yes` plus `--expected-plan-fingerprint`, re-reviews Steam and refuses a changed build. Destination validation, branch and alias checks and missing prepared sessions fail before any network request. Downloads stay in a locked sibling staging folder; only a fully verified tree containing the dedicated executable is renamed into the new destination. Non-installed outcomes (`published_unbound`, `cancelled`, `failed`) return `ok: true` with exit 4 and fixed `content_error`/`auth_error` categories; inspect `data.outcome.status`. Never fall back to SteamCMD.

`server workshop list|plan|acquire|verify` uses the same native provider for Arma 3 Workshop UGC. Plan is read-only (published-file details plus a Workshop depot-key entitlement check) and validates ids, alias, repair targets and the prepared session before any request. Acquire requires `--yes` plus `--expected-plan-fingerprint` and the unchanged tracked-document generation; per-item results are independent and the batch is `complete` only when every item that needed a download was pinned, otherwise exit 4 with `partial`, `failed` or `cancelled`. `verify` exits 4 on a mismatch and 3 for an untracked item; it never writes. Never fall back to SteamCMD or the desktop Steam client.

## Foreground server metadata ownership

Native Arma lifecycle uses `server instance start-plan|start|status|stop|restart`. Start-plan verifies the exact settled active runtime without owner contact or writes. Start/Restart consume its activation generation and fingerprint; Stop/Restart also require the exact retained run generation. Real effects require an existing authenticated owner and `--yes`. Stop's1..120000ms deadline grants no force authority; explicit `--force --yes` immediately requests owned-tree termination and waits for cleanup. Incomplete/unknown/cancelled results use4 and require fresh Status. Natural/forced cleanup and readiness remain distinct. Start's fingerprint binds the visible foreground owner-exit policy (five-second soft grace, then forced save-uncertain cleanup). Status is authenticated read-only owner observation with age and always reports engine readiness as unverified. A replacement's `not_owned` status cannot clear former consumer evidence. Dry-run never contacts an owner or sends an effect. Standard JSON/TOON envelopes and early wipe refusal remain mandatory. A protected persistent controller lock and monotone cursor serialize stable request identities across CLI invocations without weakening the owner-generation ledger.

`server supervise --game-space ID` is a foreground metadata owner; it takes the captured per-space claim without opening Turso and runs until ordinary shutdown. The hidden parent-bound form is only the GUI child lifetime. `server owner --game-space ID --json` is an authenticated read-only owner client. Explicit routing distinguishes public network inspection, local metadata, owner IPC and foreground ownership; no blanket Server dispatch may open the client DB. These commands reject --wipe-db, and supervise --dry-run must not start an owner. Second owners return6. Exact snapshot/handshake failure is4; no owner is implicitly started by inspection.

Every actual offline server save retains `content::claim`'s optional authenticated metadata permit until apply and joined cleanup finish, including instance/configuration saves and controlled stage/record/preparation workers. Otherwise it uses the existing temporary local claim. Never discard the RAII return at a bare claim(...)? statement. ServerStore's offline write seam accepts only the held local claim or retained exact remote permit; neither permit nor an Inspect response resumes Turso. Pure previews retain prior no-write behavior. Native Arma Start/Stop/Restart use the separate lifecycle commands and authenticated existing foreground owner; legacy `launch-plan` and `start --dry-run` remain previews. Schema, JSON/TOON envelopes, expected revisions/fingerprints, --yes and existing exit codes stay stable.

`server installation check <instance>` compares the managed receipt's branch/build/depot manifests with native Steam read-only. `validate <instance>` is offline, hashes the complete file inventory excluding only the root receipt and returns exit 4 for content mismatch. Neither authorizes maintenance. `update|repair plan|apply` publishes a new fully verified successor and rebinds only the reviewed instance. Both require a fresh folder, prepared-session provider review and exact catalog/instance/receipt/physical identity; repair reacquires the reviewed target build, potentially newer. Retain the previous root and peer bindings. Apply holds old-root admission and exclusive content through download/publication/binding and refuses live/unresolved consumers or pending recovery; no implicit stop/restart. A post-publication cancellation or stale binding is `published_unbound`, with complete candidate retained. Retry reviews anew. Preserve existing install dry-run/yes/JSON/cancellation contracts and reject destinations nested inside other installations across spaces/config roots.

## Server Backend CLI

- For `foxy-server-backend-cli create`, preserve `appUpdateUrl` passthrough from config (`config.json`) to generated `repo.json`; if both config and `--app-update-url` are set, CLI flag wins.
- `foxy-server-backend-cli create` collects `.bikey` files into one flat folder when `--collect-keys`, `--keys-output`, or `--additional-keys` is given (default destination `<output>/keys`). Collection is opt-in, never removes existing files in the destination, and deduplicates by file name: identical keys are skipped, differing keys with the same name keep the first match and are reported.
- `foxy-server-backend-cli create` ends by printing the server launch line on its own line so wrapper scripts can grep it. The config's `game` (`arma3` default, `reforger`) picks the shape: Arma 3 prints `-mod=` with Creator DLC codes from `dlcContent` first, then enabled required mods; Arma Reforger prints `-addonsDir <prefix or .> -addons <id,...>` with each mod id read from its `.gproj` GUID (project ID, `ServerData.json` id, folder name as fallbacks). Disabled and client-side mods are never emitted, `--mod-line-prefix` sets the server-side folder prefix (the `-addonsDir` root for Reforger), and `--mod-line-include-optional` adds the optional mods. A Reforger config that sets `dlcContent` or `clientSide` gets a warning; `new --game reforger` writes a Reforger template and Reforger `repo.json` files carry `"game": "reforger"`.
- `foxy-server-backend-cli create-space <space.json> <output>` generates every repository of a repository space plus `repository_space.json`, reusing the per-repository config files. `--layout copy` (default) matches running `create` per repository; `--layout pool` copies each distinct mod once into a shared folder (`--pool-dir`, default `<output>/pool`) and symlinks the repositories to it with relative links; `--layout link` symlinks straight to the source folders and requires `--yes` because it writes manifests into the sources. A mod name shared by several repositories must hash identically everywhere; mismatches are an error, never a silent pick. Existing real directories are never replaced by symlinks. Keys are collected once for the whole space, `--per-repo-keys` additionally writes `<output>/<folder>/keys` per repository (its own keys plus `--additional-keys`, refused when a mod is named `keys`), and a `-mod=` line is printed per repository folder.
- `modLineFiles` in a repository config lists launch scripts or server configs that `create` and `create-space` rewrite with the generated launch line: only the value of each parameter (`-mod=` for Arma 3, `-addonsDir`/`-addons` for Reforger) is replaced, and quoting plus the rest of the line are preserved. Paths resolve from the config file's directory. A listed file that is missing or has no such parameter fails before generation starts, `validate` runs the same check, `--dry-run` previews the files as `update-mod-line` actions, and the rewrite happens only after the output is published.
- Both `create` and `create-space` write the printed server launch line into `server_mod_line.txt` at each generated repository root. `create` still prints its launch line last. `--prune-unused-optionals` omits root-level `optionals` folders from copied output and removes old published copies; it asks for `--yes` only when such copies exist (checked before any write, listing each folder), never edits sources, and is rejected with `--layout link`.
- `create-space --layout pool --clean --dry-run` previews orphaned generated pool mod folders and matching repository symlinks. `--clean --yes` removes them after successful generation. Cleanup never follows symlinks or removes unrecognized directories; pools outside the output require a matching prior generated inventory.
- The server CLI accepts `--json` globally and emits a single JSON result on stdout, routing human progress to stderr. `create` and `create-space --dry-run` preview planned output without writing. `--incremental` uses source and output metadata caches; `verify` rehashes generated content. `--atomic --yes` stages and replaces a whole output directory, and cannot use an external pool or keys destination. `create-space --only` preserves the full space manifest and refuses selected mods shared with unselected repositories. `--report` and `diff` compare published mod checksums and estimate client bytes from changed mod sizes. `validate`, `audit-keys`, and `export-reforger-config` are read-only except for the explicit export output.
- `foxy --version` / `foxy version` print the release version derived by `build.rs` from the first `# MAJOR.MINOR.PATCH` heading in `CHANGELOG.md`; all application version consumers use `crate::build_info::VERSION`. `foxy-server-backend-cli --version` retains its own package version. Both include the source commit (`1.2.0 (a1b2c3d)`, `-dirty` when built from a modified tree, `-dev` for debug builds) so a build from source can be told apart from the published artifact of the same version. Keep the compile-time commit when changing either build script.

- Foreground instance status preserves data.status and adds data.monitoring. Monitor and logs read authenticated generation-bound sanitized cache snapshots, without opening Turso or triggering queries. Query traffic belongs to the explicitly started retained run. Normal --json stays one result; only monitor --follow --stream-json emits framed NDJSON snapshots/end/error, deduplicates log sequences and marks run changes. Reject --stream-json with global --json/--toon and interval without follow. Dry runs preview without owner contact; cancellation joins the local reader without stopping the server. Cached logs cap128lines/32KiB, resource history60samples, query-attempt history16. Health covers process and A2S only; query-ready is separate from native game/scenario readiness. Runtime protocol 7 binds the optional observation digest without raising control payload limits; per-HC status travels in that digest-bound snapshot (`headless`, at most 32 entries), not in the control reply.
- `server headless list|add|set|remove|plan|status|start|stop|restart` edits Arma HC definitions, including their lifecycle policy (`--manual-start`, `--start-delay`, `--join-timeout`, `--max-restarts`), through ordinary revision-checked draft changes (`set` replaces one definition and keeps its id; remove needs `--yes`), reviews committed HC launch plans from the start-plan review, and reads or changes HCs only through the authenticated owner. `status` prints the owner-observed per-HC entries of the current run (`data.clients`, `ready_unix_ms`, `query_ready`); `join` evidence is reported as `pending`, `joined` or `no_evidence`, never inferred from a live process. `start`, `stop` and `restart` need `--expected-run-generation` and `--yes`, accept `--client <hc-id>` for one HC, and their `--dry-run` prints the exact owner operation without contacting the owner. Start and restart refuse unless the same run is query-ready; stop and restart take `--timeout-ms`, and stop alone takes `--force`. Reforger and unsupported hosts reject the command group with validation errors. Plans and outputs never contain the join password or its reference.
- `server maintenance list|add|set|remove|run|cancel|history` manages per-instance scheduled jobs for spaces with a native lifecycle and rejects other games with a validation error. `add`/`set`/`remove` are revision-checked catalog writes (`--expected-revision`; `set` replaces the definition and keeps the id; remove needs `--yes`), and their `--dry-run` previews the saved catalog without writing; a stale catalog revision, malformed ids and invalid schedules or policies exit 2. `--at` accepts RFC 3339 with an offset or `YYYY-MM-DDTHH:MM` in the job clock; `--weekly daily|mon,...` requires `--time HH:MM`; `--utc` selects the UTC clock. `list` reports `data.overview` (catalog revision, `owner_running`, per-job next run, last and open occurrence, blocker) without opening the database; `history` reports `data.occurrences` newest first plus `unreadable` and `truncated`. `run` (needs `--expected-policy-revision`) and `cancel <occurrence-id>` need `--yes` and an existing owner, return `data.occurrence_id`, `state` and `created`, and their `--dry-run` prints the owner operation without contacting it. A missing owner, a stale policy revision or a refused request exits 4.
- `server rcon configure|set-password|disable|status|test|command|history|probe` covers RCon for spaces with a native lifecycle. `configure`, `set-password` and `disable` are revision-checked draft writes that claim the space (`--expected-revision`, `--dry-run`; `disable` needs `--yes`); `--permission`/`--max-clients` are Reforger-only and rejected for Arma with exit 2. Passwords come only from one stdin line through the private input reader (hidden on a terminal, plain from a pipe); never add a password argument, environment variable or echo. `status` reports `data.draft` (no secret), `password_available`, `owner_contacted`, `session` and `session_error` without opening the database. `test` and `command` need an existing owner and a running server; `command --text` needs `--yes`, exits 0 for `replied`, 5 for `unknown` and 4 for `not_sent`, and returns `data.command_id`, `state`, `reason` and the stored `record`. `history` reports `data.history.records` newest first plus `unreadable`. `probe` opens a separate session with the active runtime's protected password or `--password-stdin`, optionally at `--endpoint`; a refused or silent login is an `ok: true` report with `data.login` and exit 4, and `--command` needs `--yes` and is sent once.

`server rcon probe --listen-ms <0..30000>` pumps the separate probe session for additional asynchronous server messages after login, keepalive and any command; the default is 300 ms. Increase it when the engine emits semantic replies later than the command ACK, such as a permission denial. An ACK confirms transport response only and never proves the requested administration effect.

- `server backup plan|create|list|verify|pin|unpin|retention|prune-plan|prune <instance-id>` uses early `ServerDatabaseUse::LocalMetadata` dispatch, rejects `--wipe-db`, never opens Turso (`database_opened: false`), and returns stable `--json`/`--toon` envelopes. Default consistency is `StoppedVerified`; `--live` opts into explicit `BestEffortLive` when running, `--expected-plan-fingerprint` and `--expected-generation` enforce optimistic concurrency (exit 2), `--dry-run` validates without writes, `verify` returns exit 4 on tampered/corrupt archives, and `prune` requires `--yes`. `server maintenance add|set` accept `--live-backup`/`--stopped-backup` to configure `policy.backup_mode` (`stopped_verified` by default).
- `server restore plan|apply|status|rollback <instance-id>` never opens Turso and returns stable JSON with `database_opened: false`. Plan is write-free; apply requires `--backup-id`, `--expected-plan-fingerprint` and `--yes`; rollback requires `--expected-journal-fingerprint` and `--yes`. `--dry-run` is write- and owner-claim-free. Restore applies only verified local save/profile files from a stopped-verified backup after exact retained compatibility checks; it does not download engine content or convert saves. Pending recovery blocks activation, Start and new backups until status/rollback resolution.
