# Foxy Turso write profiling

Use this workflow for DB write throughput, sync persistence, checkpoints, or write-amplification questions. Read [core conventions](../../conventions/CORE_CONVENTIONS.md), [speed-of-light conventions](../../conventions/SPEED_OF_LIGHT.md) O7 and collection rules, [measurement archive](../../conventions/SPEED_OF_LIGHT_MEASUREMENTS.md), and [testkit skill](../foxy-testkit/SKILL.md).

The Turso seam is `src/core/db/`; initialization and DB work are in `src/core/tasks/db_turso.rs`, with sync persistence in `src/core/api/sync_pipeline/hashing.rs`. Inspect transaction ownership, process-lock acquisition, and current statement instrumentation before interpreting a measurement.

## Define the workload

- Name the action and distinguish `db_persist`, `db_purge`, bootstrap, compaction, and download-report timings. A legacy log label containing SQLite does not change the current Turso engine.
- Freeze row counts and shapes, indexes, statement kinds, transaction size, write gate, pool, schema, engine version, database mode, storage volume, and initial state.
- Attribute statements to phases and classify every affected row as insert, update, or delete where the contract requires it. Mixed or missing classifications cannot receive a gate-calibrated ratio.
- Compare DB service time and action wall time separately. Parallel sums, queue wait, checkpoint, and other action stages must not be mislabeled as DB execution.
- Gate 1 is the uncontended writer reference. At higher gates, transaction windows can include Turso's internal writer queue while permit-wait counters stay small; do not interpret a longer window as more row work. Only classify a calibrated row-cost ratio when the convention's operation-kind and gate conditions hold.
- Keep profiled runs separate from unprofiled results. Per-call instrumentation can perturb DB/filesystem-bound cases.
- Use the testkit DB calibration workload only as its stated reference. It is not an application baseline for a different row shape or storage device.
- Preserve one-process ownership of each game-space database. Never open, copy, mutate, compact, or benchmark a user's runtime DB as a diagnostic shortcut.
- DB/schema changes must follow the Turso seam and schema/version rules in core conventions; do not manually patch runtime files.

For each statement interval, retain:

- The SQL operation class and affected row count where available.
- The owning action and phase label.
- Transaction begin/commit boundaries and gate occupancy.
- Checkpoint, retry, and busy-wait time as separate components.
- Whether the measurement includes statement preparation or only execution.
- Any schema, index, journal, or engine configuration that differs from baseline.
- The database process lock and claimed game-space owner.
- The exact timer start and end around persistence.
- Whether row work was generated by sync, bootstrap, or maintenance.

## Evidence and stopping

Report case/run and calibration IDs, schema and engine, row/statement counts, operation and phase, gate/pool, elapsed and service intervals, memory, outcome, and matching reference conditions. State whether the evidence comes from static instrumentation review, sampled testkit runs, or verified action results.

Stop when workload attribution is complete, the result is comparable, and the claim is supported or rejected by repeated runs. If statement classification, transaction boundaries, or engine conditions are missing, mark the ratio unavailable. Do not infer a Turso bottleneck from total sync time alone.

For static review, trace DB calls through the seam and report likely query/transaction costs as hypotheses; code inspection cannot establish write throughput.

Keep read timing, write timing, and checkpoint cost distinct when the instrumentation exposes them.

Do not compare WAL and MVCC rows as interchangeable controls. Use the testkit's paired comparison path and preserve the same frozen case, recording each mode as a separate condition.
